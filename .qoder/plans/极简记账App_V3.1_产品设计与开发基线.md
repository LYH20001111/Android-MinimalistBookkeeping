# 极简记账 App V3.1 产品设计与开发基线

> **版本主题：私有云稳定性与服务器管理**  
> **版本定位：在 V3“本地优先 + 家庭自建服务器 + 可选云端同步 + 多设备一致性”的基础上，完善服务器可靠性、数据可恢复性、同步可诊断性与账号边界。**

---

## 0. 文档定位

本文基于《极简记账 V3 开发计划》的已实施结果，以及当前使用“本地电脑作为家庭服务器”进行真机联调时暴露出的产品与工程问题整理而成。

V3 已完成：

- 认证体系。
- JWT Access Token / Refresh Token。
- 设备管理。
- 服务端用户隔离。
- Push / Pull 双向增量同步。
- LWW 冲突处理。
- Conflict Log。
- Soft Delete。
- 同步队列、游标与状态。
- SyncCoordinator。
- WorkManager 重试。
- 首次同步合并确认。
- 多设备同步。
- 本地优先。
- 家庭服务器部署路径。

V3 开发计划已验证客户端 202 个 JVM 单测、19 个真机仪器测试以及服务端测试和构建。fileciteturn4file0L3-L7

V3.1 不再优先增加新的账务业务模型，而是围绕：

> **“服务器可用、数据可恢复、同步可观察、删除可找回、账号边界清楚。”**

进行一次完整收敛。

# 1. V3 当前产品状态

## 1.1 V3 已经解决的问题

当前同步体系已经具备较完整的双向同步基础：

```text
本地 Room
   ↓
同步队列
   ↓
Push
   ↓
家庭服务器
   ↓
Pull
   ↓
本地 Room
```

同时 V3 已明确：

- Server 采用接收顺序作为 LWW 的逻辑裁决顺序。
- 旧版本不能静默覆盖服务器新版本。
- 冲突写入 `conflict_logs`。
- Pull 只应用高于本地的 server version。
- 本地同步元数据包括 `syncId / version / serverReceivedAt / isDeleted`。
- 删除统一使用 Soft Delete。
- 同步失败使用重试与 WorkManager 持久化调度。fileciteturn4file0L16-L23 fileciteturn4file0L35-L48 fileciteturn4file0L51-L69

这些设计作为 V3.1 的技术基础继续保留。

---

# 2. V3.1 为什么需要独立版本

V3 已经解决：

> **“多设备的数据怎么同步？”**

V3.1 需要解决：

> **“同步依赖的家庭服务器怎么长期稳定运行？”**

以及：

> **“用户如何知道同步到底发生了什么？出了问题怎么恢复？”**

因此 V3.1 不应继续以“增加业务功能”为主要目标。

# 3. V3.1 核心目标

## 3.1 四个核心目标

### 目标 A：服务器可用

用户能够：

- 查看服务器连接状态。
- 测试服务器连接。
- 查看服务器版本。
- 查看服务器健康状态。
- 明确服务器地址。

### 目标 B：数据可恢复

用户能够：

- 删除后恢复账单。
- 创建服务器备份。
- 查看服务器最近备份。
- 在服务器异常或数据损坏时恢复。

### 目标 C：同步可诊断

用户能够知道：

- 最后同步时间。
- 待同步多少条。
- 最近拉取多少条。
- 最近发生多少冲突。
- 当前同步是否失败。
- 失败后何时重试。

高级诊断界面可以进一步显示：

```text
Push
Pull
Conflict
Retry
Server
API Version
Sync Protocol Version
```

### 目标 D：账号与本地数据边界清楚

尤其解决：

```text
账号 A
  ↓
退出
  ↓
账号 B
```

时用户不知道当前本地账本属于谁的问题。

# 11. 服务器备份

## 11.1 为什么是 P0

V3 中家庭服务器已经成为多设备同步的数据节点：

```text
手机 A ──┐
手机 B ──┼──> 家庭服务器
手机 C ──┘
```

因此服务器本身必须具备备份能力。

如果家庭电脑硬盘损坏：

> 服务器数据可能丢失，所有设备的共享同步基础都会受到影响。

# 14. 服务器备份内容

备份至少包含：

```text
users
email_verification_tokens（如仍需要恢复）
devices
refresh_tokens（恢复策略需单独决定）
categories
accounts
transactions
budgets
recurring_transactions
sync_changes
conflict_logs
```

其中：

> **认证 Token 是否进入恢复备份，需要在实现时明确。**

建议不要把仍有效的 Refresh Token 当作普通业务数据长期归档。恢复后更安全的默认行为应是：

```text
服务器恢复
↓
撤销现有设备 Refresh Token
↓
用户重新登录
```

这样可以降低备份文件泄露后的风险。

# 15. 服务器恢复

恢复是备份的对应能力。

流程：

```text
服务器管理
 ↓
选择备份
 ↓
显示备份时间 / 文件大小 / 数据统计
 ↓
确认
 ↓
停止业务写入
 ↓
恢复 PostgreSQL 数据
 ↓
恢复服务
 ↓
校验数据库
 ↓
生成恢复报告
```

恢复前必须明确警告：

> **恢复服务器数据会影响所有设备。恢复后需要设备重新同步。**

---

# 16. 服务器恢复后的同步策略

不能简单恢复数据库后继续沿用原 sync cursor。

建议：

```text
服务器恢复
 ↓
确定恢复点
 ↓
服务端生成 recovery epoch / generation
 ↓
客户端发现 generation 变化
 ↓
进入“服务器已恢复”状态
 ↓
要求重新 bootstrap / reconcile
```

V3.1 的具体协议字段待开发前冻结，但原则是：

> **服务器恢复必须被客户端感知。**

否则客户端可能继续使用恢复前游标，产生错误的增量同步判断。

# 20. 恢复机制

恢复不是简单的本地 Boolean 反转。

必须成为一条新的同步写操作：

```text
恢复
 ↓
is_deleted = false
 ↓
version + 1
 ↓
写同步队列
 ↓
Push
 ↓
其他设备 Pull
```

这样所有设备最终仍然一致。

# 30. 账号与本地账本绑定规则

建议 V3.1 明确一个本地账本的“云绑定账号”状态：

```text
LOCAL_ONLY
BOUND_TO_ACCOUNT
```

### LOCAL_ONLY

本地账本存在，但未与服务器账号绑定。

### BOUND_TO_ACCOUNT

当前本地账本绑定指定账号并参与同步。

这样未来切换账号时不会出现隐式串账。

# 37. V3.1 数据模型原则

V3.1 尽量不增加账务实体。

重点新增的是：

```text
ServerHealth
BackupMetadata
SyncDiagnosticEvent
RecoveryGeneration
```

其中如果服务器健康信息只是实时计算，可以不入库。

备份元数据和同步诊断如果只服务部署端，也可以使用服务器本地文件 / 日志存储，避免污染业务数据库。

# 45. 数据安全原则

V3.1 继续禁止：

- Token 写普通日志。
- 密码进入日志。
- 敏感备份文件明文暴露到公开目录。
- 用客户端传入的 userId 决定服务器数据范围。

V3 已明确 JWT 获取当前用户，服务端业务查询强制 `user_id = 当前认证用户`。fileciteturn4file0L132-L138

V3.1 在此基础上新增：

> **备份文件本身必须视为高敏感数据处理。**

# 49. V3.1 最终产品定义

> **V3 解决“同步起来”，V3.1 解决“可靠地同步下去”。**

V3.1 不追求增加更多业务功能，而要让用户建立三个信任：

```text
我知道服务器现在是否正常。

我知道我的数据有没有同步。

即使删错、服务器出问题，数据也有办法恢复。
```

最终主题：

> **连接可靠、数据可恢复、同步可诊断、服务器可管理。**

# 50. 文档状态

**版本：V3.1**  
**状态：产品设计与开发基线（建议评审版）**  
**上一版本：V3**  
**版本主题：私有云稳定性与服务器管理**

V3.1 正式开发前必须先确认：

1. 服务器备份 / 恢复是否由服务器管理员操作，还是允许手机端触发。
2. 恢复后采用“重新 Bootstrap”还是“Recovery Generation + 增量收敛”。
3. 回收站是否永久保留，或增加可配置保留时间。
4. 家庭服务器正式环境是否强制 HTTPS。
5. PostgreSQL 是否正式成为 Release 唯一数据库。

这些属于产品与部署策略决策；在决策冻结前，不应把实现细节写死在代码中。
