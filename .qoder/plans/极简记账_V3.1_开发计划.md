## 1. 现状盘点（开发前代码勘察结论）

### 1.1 客户端（app/，纯 Java + XML ViewBinding + MVVM）

| 模块 | 现状 |
|---|---|
| 数据库 | Room `version = 5`，手写迁移链 1→5，schema JSON 3/4/5 齐全 |
| 软删除 | 5 张可同步表（transaction/category/account/budget/recurring_transaction）已有 `is_deleted` 墓碑列，仅作同步用，**无删除时间戳，无回收站 UI** |
| 同步 | `SyncCoordinator`（Push→Pull 单飞）、`SyncEnqueuer`（脏标记入队）、`SyncScheduler`（防抖/退避/WorkManager）、`SyncPayloadMapper`、`RetryPolicy` |
| 同步状态 | Room 表 `sync_state`（status/last_sync_at/last_error/conflict_count）+ 内存 LiveData；游标按账号隔离存 `sync_cursor` |
| 网络 | Retrofit `ApiService` + `ApiClient`（统一注入 X-Api-Version=1 / X-Sync-Protocol-Version=1 / X-Device-Id；401 自动 refresh 重放） |
| 服务器地址 | `ServerConfigStore`（SharedPreferences `sync_server` / `base_url`） |
| 认证 | `TokenStore`（`sync_auth`）+ `AuthRepository`；退出登录保留本地数据 |
| 已有备份 | 仅**本地** JSON 备份/恢复（SAF），与服务器无关 |
| 缺失 | 服务器健康检查、服务器备份/恢复、回收站、同步诊断、冲突历史、账号边界 UI —— 全部为零 |

### 1.2 服务端（server/，Spring Boot 3.5.5 + Java 17 + JPA + Flyway）

| 模块 | 现状 |
|---|---|
| 数据库 | 默认 PostgreSQL，H2（PG 兼容模式）用于本地/测试；Flyway 已有 V1/V2，**下一个迁移为 V3** |
| 同步表 | 5 张业务表继承 `SyncRow`（user_id/sync_id/version/server_received_at/updated_at/is_deleted/created_at）；`sync_changes` 游标日志；`conflict_logs` 冲突审计 |
| LWW | `Lww.resolve()` + `SyncService.writeConflictLog()`，`winner` 字段已有 |
| 版本 | 协议版本常量 `API_VERSION=1`、`SYNC_PROTOCOL_VERSION=1`（`ApiVersionFilter`）；**无运行时服务器版本号端点** |
| 端点 | auth 9 个 + sync 4 个（push/pull/bootstrap summary/status），status 仅返回 `{serverTime, emailVerified}` |
| 缺失 | 健康检查、备份/恢复、冲突查询、恢复代际（epoch）、管理页 —— 全部为零 |

### 1.3 与基线的差距映射

| 基线目标 | 差距 |
|---|---|
| A 服务器可用 | 无健康端点、无版本信息、连接测试仅复用 /sync/status 且错误文案不友好 |
| B 数据可恢复 | 服务端无备份/恢复；客户端删除数据无找回入口 |
| C 同步可诊断 | 仅 5 个字段快照，无事件历史、无 push/pull 细分、无耗时 |
| D 账号边界清楚 | 游标已按账号隔离，但 UI 无绑定关系展示，退出提示未说明账本归属 |

## 2. 开发前决策冻结（对应基线第 50 节的 5 项待决事项）

| # | 决策项 | 冻结结论 |
|---|---|---|
| 1 | 备份/恢复由谁操作 | **服务器管理员操作**。管理员 = 配置项 `app.admin-emails` 中的账号；未配置时默认**最早注册的账号**为管理员（家庭服务器开箱即用）。操作入口：① 服务器内置 Web 管理页 `/admin`（主入口）；② REST API。**手机端不提供备份/恢复触发**，仅只读展示服务器健康与最近备份时间（符合基线第 40 节"客户端仅展示服务器结果"） |
| 2 | 恢复后收敛方式 | **Recovery Epoch + 游标重置重新收敛**（实现时细化）：备份**不含** `sync_changes`，恢复时按业务行当前状态重建变更日志（每行一条最新变更，id 从 1 起）；恢复时 epoch +1 并通过 `/sync/status`、Push/Pull 响应、健康端点下发；客户端发现 epoch 变化后：置"服务器已恢复"横幅 → 本地游标清零 → 全量重拉（pull 侧按版本幂等）+ **全量重推本地状态**（含墓碑，LWW 收敛到各设备最新状态）→ 记录新 epoch。**不需要重新 bootstrap** |
| 3 | 回收站保留策略 | **默认永久保留**，V3.1 不提供自动清理与彻底删除入口（协议无硬删除操作，符合基线第 21 节） |
| 4 | 是否强制 HTTPS | 不强制。家庭正式部署默认局域网 HTTP，`docker-compose.https.yml` 提供可选 Caddy HTTPS；客户端同步中心显示"安全连接 HTTPS / 未加密连接 HTTP"提示（基线第 31/32 节） |
| 5 | Release 数据库 | **PostgreSQL 为正式 Release 唯一目标数据库**；H2 仅用于开发与 JVM/集成测试（延续 V3 现状） |

**附带冻结**：
- 回收站范围：交易、分类、账户、周期账单（基线第 19 节全量支持）；被引用分类/账户仍遵循"归档优先"规则。
- 删除时间戳进入同步协议：`SyncPayload` 增加**可选字段 `deletedAt`**（epoch millis，可空），协议版本保持 1（双方同仓库同步升级，旧字段缺省兼容）；服务端业务表增加 `deleted_at` 列（Flyway V3）。
- 服务器备份文件包含：users、devices、5 张业务表、sync_changes、conflict_logs；**不包含** refresh_tokens 与 email_verification_tokens（恢复后所有设备自然要求重新登录，降低备份泄露风险，符合基线第 14 节建议）。
- 备份保留：每天 1 份 × 最近 7 天 + 每周 1 份 × 最近 4 周 + 每月 1 份 × 最近 12 月，超出即清理；同时受磁盘下限保护（剩余 < 1GB 时跳过自动备份并记录）。

## 4. 任务分解

### Phase 1：服务器连接 / 健康（基线 P0）

**服务端**
- [ ] `V3__v31_deleted_at_and_server_meta.sql`：5 张业务表加 `deleted_at BIGINT NULL`；新增 `server_meta(key, value)` 表并写入 `recovery_epoch=0`
- [ ] `common/ServerInfo.java`：运行时服务器版本常量 3.1.0
- [ ] `server/ServerHealthController`：`GET /api/v1/server/health`（公开，无鉴权），返回 `status/serverVersion/apiVersion/syncProtocolVersion/database/storage{totalBytes,freeBytes,status}/recoveryEpoch/lastBackupAt/serverTime`；磁盘水位 >20% 正常、10%~20% 警告、<10% 严重
- [ ] `SecurityConfig` 放行 `/api/v1/server/health`、`/admin/**`
- [ ] `GET /api/v1/sync/status` 扩展返回 `serverVersion/recoveryEpoch`（向后兼容，仅加字段）

**客户端**
- [ ] `ServerRepository.getHealth()`；健康模型 `ServerHealth`
- [ ] 同步中心"服务器卡片"：地址、在线状态点、服务器版本、API/协议版本、数据库/存储状态、最近检测时间、`[测试连接]` 按钮
- [ ] 连接失败文案映射（服务器关闭/地址错误/不在同一网络/防火墙），禁止裸露 SocketException 等原始异常（基线第 9 节）
- [ ] HTTP/HTTPS 安全提示（基线第 32 节）

### Phase 2/3：服务器备份 / 恢复（基线 P0）

**服务端**
- [ ] `backup/BackupProperties`：`backup-dir`（默认 `./backups`）、`daily-cron`（默认 03:00）、`auto-enabled`（默认 true）
- [ ] `backup/BackupService`：
  - 手动/定时导出全库 JSON（users → devices → 5 业务表 → sync_changes → conflict_logs，**不含 token 类表**）
  - 写入 `<backup-dir>/bookkeeping-backup-yyyyMMdd-HHmmss.json` + 同名 `.meta` 摘要（时间/大小/各表行数/epoch/serverVersion）
  - 保留策略清理（7 日 / 4 周 / 12 月）；磁盘剩余 < 1GB 跳过自动备份
  - `@Scheduled` 每日 03:00 自动备份；`server_meta` 记录 `last_backup_at/last_backup_file`
- [ ] `backup/BackupRestoreService.restore()`：校验 → 写屏障（阻塞同步写入）→ 单事务清库重建 → `recovery_epoch +1` → 生成恢复报告（各表行数 + 新 epoch）
- [ ] `common/SyncWriteBarrier`（ReentrantReadWriteLock）：push/pull/bootstrap/deleteAccount 取读锁，恢复取写锁，备份取读锁
- [ ] `backup/BackupController`（全部要求管理员）：
  - `GET /api/v1/server/backup` 列表；`POST /api/v1/server/backup` 立即备份
  - `GET /api/v1/server/backup/{name}/meta` 详情；`POST /api/v1/server/backup/{name}/restore` 恢复（响应含恢复前警告语义说明）
  - `GET /api/v1/server/stats` 管理页统计（用户/设备/交易计数 + 磁盘 + 最近备份）
- [ ] `common/AdminGuard`：管理员判定（admin-emails 配置优先，否则最早注册账号）
- [ ] 内置 Web 管理页 `resources/static/admin/index.html`（单文件，无外部依赖）：登录 → 健康/统计/备份列表 → 立即备份 → 恢复（双重确认 + 警告文案"恢复会影响所有设备，恢复后设备需重新登录并重新同步"）
- [ ] `PushResponse/PullResponse` 增加 `recoveryEpoch`（可空兼容）；`run-local.bat`、`docker-compose*.yml`、`Dockerfile`、`README` 适配新版本号与备份目录卷
- [ ] 测试：备份→再写入→恢复→数据还原 + epoch 递增 + 保留清理；健康端点公开访问与字段完整性

### Phase 4：回收站（基线 P0）

**客户端**
- [ ] Room 5→6：5 张业务表加 `deleted_at INTEGER NULL`；`sync_state` 加 `last_push_at/last_pull_at/last_push_count/last_pull_count/last_duration_ms/recovery_epoch/bound_account_email`；新增 `sync_events` 表（保留 50 条）；`MIGRATION_5_6` + MigrationTest
- [ ] `SyncPayloadMapper`：5 类载荷增删 `deletedAt` 映射
- [ ] `BookkeepingRepository`：删除时写 `deletedAt=now`；新增 `restoreTransaction/restoreCategory/restoreAccount/restoreRecurring`（isDeleted=false、deletedAt=null、入同步队列按 UPSERT 重建载荷，跨设备最终一致）
- [ ] DAO：回收站查询（`is_deleted=1`，按 `COALESCE(deleted_at, updated_at) DESC`）
- [ ] `RecycleBinActivity`（我的 → 数据管理 → 回收站）：分类型 Tab 展示 + 单条/批量恢复 + 空态文案；确认恢复即入队同步
- [ ] 测试：Migration 5→6、恢复后载荷重建（UPSERT 覆盖排队中的 DELETE）、DAO 查询

### Phase 5：同步诊断（基线 P0）

**客户端**
- [ ] `SyncCoordinator`：每轮同步记录 push/pull 计数、耗时、结果、错误 → `sync_events`（裁剪至 50 条）；更新 `sync_state` 新字段
- [ ] 服务端 Push/Pull 响应 `recoveryEpoch` 检测：变化 → 游标清零全量重拉 + 持久新 epoch + 同步中心横幅"服务器已恢复，已重新同步"
- [ ] 同步中心新增：最近拉取条数、同步耗时、最后错误、`高级诊断 >` 入口
- [ ] `SyncDiagnosticsActivity`：Server/API/协议版本、Last Push/Pull、Push/Pull/Conflict/Retry 计数、Last Error、同步事件历史列表（时间/结果/Push n / Pull n/耗时）
- [ ] 诊断数据不含 Token/密码（仅摘要与错误码，基线第 45 节）

### Phase 6：冲突历史（基线 P1）

**服务端**
- [ ] `GET /api/v1/sync/conflicts?limit=50`（登录用户维度）：返回 conflict_logs 最近记录（entityType/syncId/winner/baseVersion/serverVersion/deviceId/createdAt）；补齐 SERVER 胜出场景的冲突日志写入（当前仅 CLIENT 胜出落库）

**客户端**
- [ ] `ConflictHistoryActivity`：列表项 = 时间 + 实体摘要（本地按 syncId 反查名称/金额，查不到显示实体类型）+ "结果：采用服务器版本 / 保留本机修改"；不弹窗、不阻断（基线第 27 节）
- [ ] 同步中心冲突行 → 点击进入冲突历史

### Phase 7：账号边界（基线 P1）

**客户端**
- [ ] 同步中心"当前账号"卡片：邮箱、同步目标服务器、连接状态；开启同步时记录 `bound_account_email`
- [ ] 本地账本绑定展示：`LOCAL_ONLY / BOUND_TO_ACCOUNT(邮箱)`；当前登录账号 ≠ 绑定账号时显示醒目提示（防隐式串账，基线第 30 节）
- [ ] 退出确认对话框采用基线第 29 节文案："本地账单不会自动删除。下次登录其他账号时，当前本地账本不会自动变成新账号的数据。"

### Phase 8/9：PostgreSQL 真环境回归 / 性能（基线 P0-P2）

- [ ] docker-compose 环境变量补齐（ADMIN_EMAILS、备份目录卷）；`README` 更新部署与 API 说明

## 7. 验收标准（对照基线第 47 节）

- [ ] 同步中心可见：在线状态、服务器版本、API/协议版本、数据库/磁盘状态、测试连接
