# 极简记账 App V1.1 产品设计与开发基线

> **版本主题：时间选择与时间浏览体验完整收敛**  
> **上一版本：V1.0**  
> **目标版本：V1.1**  
> **开发平台：Android / Java / Room / Material 3**

---

## 0. 文档定位

本文是在《极简记账 App V1.0 开发方案》的基础上，结合 V1 实际运行中发现的问题，对**日期选择、周期浏览、周期跳转、空状态、时间语义**进行一次集中优化后形成的 V1.1 开发基线。

V1.1 不重新设计整个 App，不改变“记录 / 图表 / 我的”三 Tab 的总体信息架构，重点解决一个核心问题：

> **用户在任何时间点选择、查看、跳转周期时，都应该知道自己正在看什么，并且能够随时继续移动或回到当前周期。**

V1.0 的基础技术与产品边界继续保留，除本文件明确修改的项目外，其余沿用 V1.0 基线。

V1.0 已确认的基础技术与产品决策包括：三 Tab（记录 / 图表 / 我的）、Java、Room、本地优先、无网络权限、金额使用 `long` 以“分”为单位保存、图表使用自绘 Canvas View、不引入第三方图表库。fileciteturn0file0

# 1. V1.1 版本目标

## 1.1 一句话目标

> **让“选日期 / 选周期 / 浏览时间”从简单的控件操作，变成完整、连续、不会迷路的时间浏览体验。**

## 1.2 V1.1 只聚焦三件事

### 目标 A：日期选择时就能知道当天有没有账单

记录页日期弹窗不仅选择日期，还要显示该日期的：

- 支出：`-¥X.XX`
- 收入：`+¥X.XX`
- 如果没有账单流水：**不显示金额**

### 目标 B：图表空周期不能让用户“迷路”

周期导航必须始终保留。

即使某个周 / 月 / 年没有账单，也只能让“数据区域”进入空状态，不能把周期导航一起隐藏。

### 目标 C：周期导航支持直接跳转

用户点击周期导航中间的当前周期区域，可以打开周期选择弹窗，直接选择较远周期，避免连续点击 `Prev / Next`。

周、月、年统一使用这一交互模式。

# 3. V1.0 实际问题复盘

## 3.1 问题一：日期选择器信息量不足

V1 的记录页日期按钮使用 `MaterialDatePicker`，选择日期后仅更新 `businessDate`。现有实现没有在日期弹窗中告诉用户这个日期对应的账单情况。fileciteturn0file3

V1.1 要把日期选择器从：

> **纯日期选择器**

升级为：

> **带账单摘要的日期选择器**

---

## 3.2 问题二：记录页“今日”语义不准确

V1 的 XML 中字段名称是：

- 今日支出
- 今日收入
- 结余

但 `RecordViewModel` 实际计算的是 `businessDate` 对应日期的统计，而不是永远的系统今天。fileciteturn0file5 fileciteturn0file6

因此当用户选择昨天时，UI 仍然显示“今日支出”，会形成语义错误。

### V1.1 修复

统一改为：

- **当日支出**
- **当日收入**
- **结余**

“当日”明确指当前所选业务日期。

---

## 3.3 问题三：图表空周期覆盖整个内容区域

V1 图表页在周期没有记录时，会隐藏图表并进入完整空状态。

这个设计在“第一次进入、当前周期没有数据”时没有明显问题，但当用户使用 Prev / Next 主动浏览历史周期时，会出现：

```text
当前周期
  ↓
上一周期
  ↓
没有记录
  ↓
整个内容区变成空状态
```

如果空状态把周期导航一并覆盖，用户就缺少明显的继续浏览路径，甚至无法方便回到原周期。

### V1.1 修复

固定页面层级：

```text
周期类型
↓
周期导航
↓
数据区域
```

数据区域有两种状态：

```text
有数据 → 正常图表
无数据 → 空状态
```

**周期导航始终存在。**

---

## 3.4 问题四：Prev / Next 只能逐周期移动

V1 的周期导航采用 `Prev / Current / Next` 模式，适合附近周期浏览，但不适合跳转到很远的周、月、年。V1 原始方案也明确采用这一周期导航设计。fileciteturn0file0

### V1.1 修复

中间当前周期区域变成可点击入口：

```text
‹     2026年9月     ›
      ↑ 点击
```

点击后打开对应周期选择器。

# 4. V1.1 核心交互原则

## 4.1 时间控件统一原则

整个 App 的时间控件统一遵循：

> **快速移动 + 直接选择 + 当前状态可感知**

因此：

### 记录页

```text
日期按钮
→ 日历
→ 每日账单摘要
```

### 图表页

```text
Prev ← 当前周期 → Next
        ↓
      点击
        ↓
   周期选择器
```

---

## 4.2 空状态不应该破坏导航

所有“无数据”状态必须是**内容状态**，不能是**页面结构状态**。

错误：

```text
整个图表页面
↓
本周期还没有记录
```

正确：

```text
图表类型
↓
周期导航
↓
本周期还没有记录
```

# 7. 记录页“当日概览”语义修正

## 7.1 V1

```text
今日支出
今日收入
结余
```

## 7.2 V1.1

```text
当日支出
当日收入
结余
```

### 数据含义

```text
当日支出 = 当前业务日期的支出
当日收入 = 当前业务日期的收入
结余 = 当日收入 - 当日支出
```

不会因为选择历史日期而产生“今日”误导。

# 8. 记录页历史账单策略：V1.1 暂不改模型

V1 当前代码通过：

```text
observeTransactionsUpTo(date)
```

查询“截至所选业务日期”的全部账单，并通过 `StatisticsCalculator.groupByDay()` 做日期分组。`RecordUiState.rows` 也明确描述为“日期不晚于业务日期的全部账单”。fileciteturn0file5 fileciteturn0file4

这一点属于**产品信息架构决策**，不是本轮必须修改的 Bug。

### V1.1 处理原则

本版本暂时不改为：

```text
date == selectedDate
```

而是保留 V1 历史账单模式，重点先解决：

- 日期选择的可感知性
- “今日”文案错误
- 日期切换体验
- 列表刷新稳定性

后续如果确认“选择某日只看当天”的产品模式更合理，再单独作为 V1.2 / V2 设计变更评估。

# 18. 空周期中的“记一笔”行为

用户在空周期点击：

> `记一笔`

默认新增账单日期应该是：

> **当前正在浏览的周期对应日期**。

之前 V1 的“记录页新增”默认日期是当前业务日期；V1.1 的“图表空周期新增”需要额外定义周期锚点日期。

# 22. 日历摘要数据层设计

为了实现“日期下面显示当天收入/支出”，不建议让日期选择器加载整个交易明细列表再自行计算。

建议新增日期聚合查询。

## 22.1 新增 POJO

```java
DailySummary {
    long day;
    long expense;
    long income;
    int transactionCount;
}
```

## 22.2 TransactionDao

建议新增：

```java
LiveData<List<DailySummary>> observeDailySummaries(
        long startDay,
        long endDay
);
```

SQL 聚合逻辑：

```text
GROUP BY date
```

按：

```text
date ASC
```

返回指定时间范围内每天的：

- expense
- income
- count

这样日期选择器只拿聚合结果，不读取完整账单明细。

# 34. 周序号规则

V1.1 需要统一周序号算法，否则不同年份可能出现：

```text
Week 1
```

含义不一致。

建议所有 Week 文案只用于 UI 定位，不作为数据库主键。

周期真正唯一标识仍然使用：

```text
weekStart
```

即：

> **周一 00:00 的 epoch millis**

这样可以避免单纯依赖“第几周”导致跨年混淆。

# 36. 数据库约束优化建议

V1 数据库当前 `Transaction.categoryId` 使用 `onDelete = CASCADE`，同时分类管理又规定“分类被账单使用时禁止删除”。这两个语义存在潜在冲突。fileciteturn0file0

V1.1 建议调整为：

> **RESTRICT / NO ACTION**

即数据库也不允许通过删除分类级联删除账单。

### V1.1 原则

```text
业务层：禁止删除已使用分类
+
数据库层：禁止级联删除交易
```

这样更安全。

这一项虽然不是时间功能，但属于 V1.1 检查出的安全性问题，建议随本次数据库版本升级一起处理。
