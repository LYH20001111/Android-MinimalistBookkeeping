# 极简记账 App V2 产品设计与开发基线

> 基于 V1.1 “时间选择与时间浏览体验”完成后的下一阶段产品基线
>
> V2 核心主题：**从“记账 + 看统计”升级为“账户 + 资金流 + 搜索管理 + 数据安全 + 预算控制”**

---

## 0. 文档定位

### 0.1 文档目的

V2 建立在 V1.1 的产品与技术基础之上。V1.1 主要收敛了日期选择、周/月/年周期浏览、空状态和时间导航体验；V2 不再继续堆叠图表，而是补齐个人记账真正开始变得重要的几类能力：

1. **钱从哪里来、现在在哪个账户里**：账户体系。
2. **账户之间的钱移动是不是收入/支出**：转账体系。
3. **过去的账怎么找**：搜索与筛选。
4. **手机坏了怎么办、怎么把账带走**：备份/导入/导出。
5. **不仅有总预算，还能控制具体消费类型**：分类预算与预算提醒。
6. **固定收入/固定支出是否需要重复记录**：周期账单。

### 0.2 V2 产品定位

> **极简记账 V2：一个以快速记账为入口、以账户资金流为骨架、以搜索分析和预算控制为核心的个人记账工具。**

核心闭环进一步升级为：

```text
V1 / V1.1
记 → 看 → 懂 → 控

V2
记 → 入账 → 分账户 → 搜索 → 分析 → 预算 → 周期化
```

# 二、V1.1 潜在问题复盘

> 这一部分基于你提供的 V1 / V1.1 开发文档进行静态方案检查。当前对话中没有提供“V1.1 已实施后的完整源码”，因此以下标记为“潜在风险”，不是对当前运行代码的确定性判定。

## 2.1 P0 / P1：建议在 V2 前修掉的技术风险

### 风险 A：周序号跨年可能出现重复或歧义

V1.1 使用 `Calendar.WEEK_OF_YEAR` 展示 `Week N`，并设置周一为一周第一天、最少四天规则。这个思路接近 ISO 周，但仅显示 `Week 1` / `Week 5` 时，在跨年场景可能出现多个不同年份都叫 `Week 1`。

例如一个周期选择器长期存在多个年份数据时：

```text
Week 1
01.01-01.07

Week 1
01.02-01.08
```

用户可能无法快速判断属于哪个年份。

### 建议

V2 的周期选择器统一显示：

```text
2026 · Week 1
01.05 - 01.11
```

或者中文：

```text
2026年第1周
01.05 - 01.11
```

同时内部使用“周期 start + end”作为唯一身份，不使用标题文本做身份。

---

### 风险 B：`CalendarSummaryDialog` 回调接口可能存在配置变更风险

V1.1 方案要求 `CalendarSummaryDialog` 通过 `OnDateSelectedListener` 回调 `RecordFragment`。DialogFragment 在配置变化/进程重建后如果只依赖运行时设置的匿名 Listener，存在回调对象丢失的风险。

### 建议

V2 起统一改成：

> `FragmentResult API` 或共享 ViewModel

例如：

```text
CalendarSummaryDialog
        ↓
setFragmentResult("calendar_date_selected")
        ↓
RecordFragment
        ↓
RecordViewModel.setBusinessDate()
```

这样跨配置变化更稳。

---

### 风险 C：`observeDayCounts()` 全量加载每天统计，数据量大后会产生无必要开销

V1.1 方案中的周期选择器查询：

```sql
SELECT date AS day, COUNT(*) AS transactionCount
FROM transactions
GROUP BY date
ORDER BY date ASC
```

然后 Java 侧再聚合成周/月/年。对于个人用户小数据量可以接受，但账单积累几年后，每次周期选择器刷新都可能读取全部日期聚合结果。V1.1 作为 MVP 没问题，V2 应该开始限制查询范围或直接在数据库中做周期聚合。

### 建议

V2 新增：

```text
countByWeek(start, end)
countByMonth(start, end)
countByYear(start, end)
```

或者针对选择器只查询“当前可见窗口”的统计数据。

---

### 风险 D：日历单格信息密度较高

V1.1 要求日期格同时显示：

```text
日期
-¥X.XX
+¥X.XX
```

在小屏设备、系统字体放大、金额较大时，56dp 左右的单格高度可能出现截断/拥挤。

### 建议

V2 保留信息，但组件必须支持：

- 金额单行显示。
- 超长金额自动紧凑格式。
- 无收入/支出时不占高度。
- 系统字体放大后仍不重叠。
- 日历网格使用独立的组件 Token，不硬编码 56dp / 10sp。

---

### 风险 E：业务日期用 epoch millis 长期存在时存在时区迁移风险

当前 V1/V1.1 业务日期使用“本地当天 00:00 的 epoch millis”。这种做法在普通场景稳定，但用户修改时区、跨时区旅行或系统进行时区切换时，需要非常小心。

### 建议

V2 不必强制马上重构整个 V1 数据，但新增业务能力时建议逐步统一为：

```text
businessDate = yyyy-MM-dd
createdAt / updatedAt = epoch millis
```

也就是说：

> “业务日期”与“时间戳”分离。

这对未来云同步、多设备、跨时区非常重要。

---

### 风险 F：分类删除规则应保持数据库层与业务层一致

V1 文档中最初使用了 `onDelete = CASCADE`，V1.1 计划已经改为 `RESTRICT`，并同步升级数据库版本。这个方向是正确的。V2 必须继续保留：

```text
分类已被账单使用
→ 禁止直接删除
→ 可以停用 / 归档
```

V2 增加账户与转账后，所有外键删除策略也应统一采用“禁止误删财务数据”的原则。fileciteturn1file0L69-L100

# 三、V2 产品目标

## 3.1 三个核心升级

### 升级 1：从“账单”升级到“资金账户”

V1 只知道：

> 我花了多少钱。

V2 开始知道：

> 我的钱现在在哪。

例如：

```text
现金       ¥500
微信       ¥2,300
支付宝     ¥1,280
银行卡     ¥8,600
信用卡     -¥1,200
```

---

### 升级 2：从“记账记录”升级到“资金流”

例如：

```text
微信 → 银行卡 ¥1,000
```

不能记成：

```text
收入 +¥1,000
```

也不能记成：

```text
支出 -¥1,000
```

而应该定义成：

> 转账。

---

### 升级 3：从“看数据”升级到“找数据 + 控数据”

用户可以：

```text
搜索“星巴克”
筛选“餐饮”
筛选“支出”
筛选“微信”
筛选“100～500元”
筛选“2026年8月”
```

同时可以设置：

```text
总预算 ¥5,000
餐饮预算 ¥1,200
交通预算 ¥500
```

# 八、余额模型必须先定义清楚

这是 V2 最重要的数据设计之一。

不能简单地把：

```text
账户余额 = 上次余额 - 支出 + 收入
```

散落在 UI 代码里计算。

统一规则：

```text
当前余额
=
初始余额
+ 收入
- 支出
+ 转入
- 转出
```

对于信用卡，可根据账户类型采用：

```text
负数 = 欠款
```

V2 第一版建议先采用“余额可正可负”的统一模型，避免单独设计另一套信用卡账务模型。

# 九、V2 转账

## 9.1 转账入口

在“新增记录”页增加：

```text
支出 | 收入 | 转账
```

选择“转账”：

```text
转出账户
微信

转入账户
银行卡

金额
¥1,000.00

日期
2026-09-03

备注
工资转存

保存
```

---

## 9.2 转账业务规则

转账：

- 不计入收入。
- 不计入支出。
- 不计入消费统计。
- 不影响总资产。
- 只影响不同账户余额。

例如：

```text
微信 -¥1,000
银行卡 +¥1,000
```

总资产不变。

---

# 十、建议的交易模型升级

V1：

```text
Transaction
```

继续统一：

```text
Transaction
│
├── EXPENSE
├── INCOME
└── TRANSFER
```

新增字段：

```text

```

含义：

```text

收入：account_id 有值
转账：account_id + transfer_account_id 都有值
```

这样可以最大限度复用 V1 的统计与历史账单基础。

# 十四、V2 数据导入

导入不能直接“读 CSV → 全部插入”。

```text

 ↓

 ↓

 ↓

 ↓

 ↓

 ↓
```

# 二十三、数据库唯一约束与安全规则

## Account

账户名称不强制全局唯一，但建议同一用户环境下避免完全相同名称。

## Budget

唯一键：

```text
(year, month, category_id)
```

其中 `category_id = null` 表示总预算。

## Transaction

不删除历史账单主键。

## Account

被历史账单使用后：

```text
禁止物理删除
→ 只允许归档
```

这是 V2 必须采用的原则。

# 三十四、V2 为什么暂时不做云同步

这是产品策略上的刻意延后，而不是技术上不能做。

V2 先解决：

```text

账户
转账

```

等本地财务模型稳定后，再建立云同步。

否则如果 V2 同时做：

```text

导入
云同步
登录
```

数据库与同步逻辑会同时变动，开发风险很高。

# 三十七、V2 最终版本定义

> **V2 不是“增加更多图表”，而是让记账从“记录一笔消费”正式升级成“管理个人资金流”。**

V2 的四个核心问题：

```text
1. 我的钱现在在哪？
   → 账户

2. 钱为什么发生变化？
   → 收入 / 支出 / 转账

3. 过去的账怎么快速找到？
   → 搜索 / 筛选

4. 怎么保证账不会丢，并控制未来消费？
   → 备份 / 导入导出 / 分类预算 / 周期账单
```

因此 V2 的产品关键词确定为：

> **账户化、可追溯、可搜索、可迁移、可控制。**
