# 极简记账 App V5
## 扫描账单 / AI 智能记账产品设计与开发基线

> **文档定位**
>
> 本文档只定义 **“扫描账单”** 与 **“AI 智能记账”** 两项增强能力的产品与开发方案。
>
> **核心原则：手动记账始终是主体，不改变原有“记一笔”页面的主流程。**
>
> 在现有“记一笔”页面右上角增加增强入口：
>
> `扫描账单` / `AI 智能记账`
>
> 两种能力最终都进入统一的“账单确认”环节，再由用户确认后写入正式账单。

---

# 1. 产品目标

## 1.1 核心目标

让用户在不改变原有手动记账习惯的前提下，获得两种更快捷的增强方式：

### 扫描账单

> 用户提供小票、消费凭证、账单截图等图片，App 自动识别并填充账单信息。

### AI 智能记账

> 用户通过自然语言输入或语音描述消费情况，App 自动理解金额、类型、分类、日期、备注等信息并生成账单草稿。

---

# 2. 产品定位

本功能不是独立的“AI 工具”，而是：

> **手动记账页面中的智能辅助能力。**

产品关系：

```text
                         记一笔
                           │
                ┌──────────┴──────────┐
                │                     │
             手动输入                增强能力
                │                     │
                │             ┌───────┴───────┐
                │             │               │
                │          扫描账单       AI 智能记账
                │             │               │
                │             └───────┬───────┘
                │                     │
                └─────────────┬───────┘
                              ↓
                         账单草稿
                              ↓
                         用户确认/修改
                              ↓
                           保存账单
```

因此：

- 手动记账不会被替代
- AI/OCR 不增加独立一级导航
- AI/OCR 不改变原有新增账单页面的信息架构
- AI/OCR 的目标是减少输入，而不是增加操作

# 4. 入口设计原则

## 4.1 不改主按钮

原有：

> 保存记录

仍然是页面最重要操作。

---

## 4.2 不把 AI 放到 FAB

不要改成：

```text
+
├── 手动
├── OCR
└── AI
```

原因：

> 会改变用户原来的记账入口认知。

---

## 4.3 增强入口应该“存在，但不打扰”

建议：

- 右上角小图标
- 初次使用可以轻提示一次
- 后续不重复强提示
- 不出现大面积 AI Banner
- 不用“AI 黑科技”等营销式文案

推荐文案：

> `智能记账`

```text

```

# 5.6 OCR 第一阶段识别字段

核心字段：

| 字段 | 优先级 |
|---|---:|
| 金额 | P0 |
| 日期 | P0 |
| 商家 | P0 |
| 时间 | P1 |
| 商品/消费描述 | P1 |
| 小票号 | P2 |

真正需要写入账单的核心字段：

```text
amount
date
time
merchant
description
```

---

# 5.7 AI 结构化解析

OCR 原始结果可能是：

```text
麦当劳
2026/09/25 12:36
午餐套餐
42.00
```

AI 结构化为：

```json
{
  "type": "expense",
  "amount": 4200,
  "date": "2026-09-25",
  "time": "12:36",
  "merchant": "麦当劳",
  "category": "餐饮",
  "note": "午餐套餐"
}
```

> 金额内部仍使用“分”作为整数，不允许使用浮点金额。

---

# 6. OCR + AI 的职责划分

OCR 不负责：

> 理解业务。

OCR 负责：

> 从图片中读取文字。

AI 负责：

> 理解文字并转换为账单字段。

因此：

```text
图片
 ↓
OCR
 ↓
文本
 ↓
AI
 ↓
结构化账单
```

# 8. 识别置信度

每个识别字段内部都可以保存：

```text
confidence
```

示例：

```text
金额     0.99
日期     0.96
商家     0.93
分类     0.87
```

UI 不要求把数字置信度展示给普通用户。

建议显示为：

### 高置信度

正常显示。

### 中置信度

轻量提示：

> `请确认`

### 低置信度

明显提示：

> `未能准确识别，请手动填写`

# 9. OCR 失败处理

## 情况 A：图片模糊

提示：

> 图片不够清晰，请重新拍摄。

按钮：

```text
重新拍摄
选择其他图片
```

---

## 情况 B：无法找到金额

显示：

> 未识别到明确金额，请手动填写。

然后直接进入现有“记一笔”表单，并保留已经识别成功的信息。

---

## 情况 C：识别到多个金额

例如小票：

```text
商品金额
优惠
实付
```

AI 应优先判断：

> 实际支付金额

如果无法可靠判断：

> 标记“请确认”。

# 10. 扫描账单的核心原则

OCR 失败以后：

> **用户仍然可以继续完成手动记账。**

所以：

```text

 ↓
失败
 ↓
不能阻断
 ↓
回到手动记一笔
```

而不是：

```text
OCR失败
 ↓
流程结束
```

# 11. 功能二：AI 智能记账

# 11.1 功能定义

用户不填写表单，而是：

> 用一句话告诉 App 自己做了什么消费。

例如：

```text
“今天中午吃饭花了32块”
```

AI 解析：

```text
类型：支出
金额：¥32
分类：餐饮
日期：今天
备注：午餐
```

然后进入：

> 账单确认。

# 19. AI 智能分类

AI 主要价值之一是：

> 自动判断分类。

例如：

```text
“星巴克买了一杯咖啡35”
```

结果：

```text
🍚 餐饮
```

---

# 20. 分类判断优先级

推荐采用：

```text
用户明确指定
      ↓
历史消费习惯
      ↓
商户识别
      ↓
AI 语义判断
      ↓
默认分类
```

例如用户说：

> “打车32，算交通”

最终必须：

> 交通

不能被 AI 改成其他分类。

---

# 21. AI 不应该擅自修改用户输入

用户：

> “买书 88 元，算教育”

AI 必须：

```text
分类：教育
```

而不是：

```text
分类：购物
```

# 25. Validation Layer

AI 输出之后必须经过独立校验。

校验：

```text
amount > 0
type 合法
categoryId 合法
date 合法
time 合法
```

例如 AI 返回：

```json
{
  "amount": -300
}
```

不能进入数据库。

必须：

> 校验失败 → 人工确认。

---

# 26. AI 输出必须结构化

不要让模型返回纯自然语言：

```text
“用户好像花了32元，应该属于餐饮……”
```

应该强制返回：

```json
{
  "type": "expense",
  "amount": 3200,
  "category": "餐饮",
  "date": "2026-09-25",
  "time": "12:30",
  "note": "午餐"
}
```

应用层只接受合法结构。

# 32. 图片处理策略

默认：

> OCR 完成后立即释放临时图片。

原则：

```text
用户选择图片
 ↓
临时缓存
 ↓
OCR
 ↓
AI解析
 ↓
生成草稿
 ↓
删除临时图片
```

除非未来明确增加：

> “保存票据附件”。

V5 不默认保存原始消费图片。

---

# 33. 隐私设计

用户应该知道：

### 本地处理

提示：

> 图片仅用于本次识别。

### 云端处理

如果 AI/OCR 需要上传：

提示：

> 图片/文本将发送至 AI 服务进行识别。

并且：

- 不默认长期保存原始图片
- 不把 OCR 原图自动上传到个人资料
- 不将用户账单文本用于非本功能目的
- 云端调用失败时允许继续手动记账

# 34. 网络状态

AI 功能可以依赖网络，但：

> **普通手动记账不应该依赖网络。**

因此：

```text
手动记账
→ 始终可用

OCR / AI
→ 网络可用时工作
```

没有网络：

```text
AI/OCR
→ 提示当前无法使用

手动记账
→ 正常使用
```

# 56. 最终产品原则

整个 V5 只坚持一句话：

> **手动记账是主流程，AI/OCR 是帮用户少输入几步的增强工具。**

所以最终用户体验应该是：

```text
普通用户：
打开记一笔
→ 正常手动填写
→ 保存

需要更快：
打开记一笔
→ 右上角
→ 扫描账单
→ 确认
→ 保存

不想填写表单：
打开记一笔
→ 右上角
→ AI 智能记账
→ 说一句话
→ 确认
→ 保存
```

三条路径最终进入同一个：

```text
TransactionDraft
      ↓
用户确认
      ↓
正式账单
```

这样既不会破坏原有记账习惯，又可以把 AI/OCR 的价值直接放到“**减少输入成本**”这个核心场景里。
