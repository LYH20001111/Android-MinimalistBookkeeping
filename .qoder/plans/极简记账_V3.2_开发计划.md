# 1. V3.1 代码现状盘点（计划的事实基础）

## 1.1 服务端（Spring Boot 3.5.5 / Java 17 / JPA / Flyway / PostgreSQL，测试用 H2 PG 模式）

| 项 | 现状 |
|---|---|
| Flyway | 最新 V3（业务表补 `deleted_at` + `server_meta`/recovery_epoch） |
| 业务表 | `categories / accounts / transactions / budgets / recurring_transactions`，全部 `UNIQUE(user_id, sync_id)`，带 `version / server_received_at / is_deleted / deleted_at`；**无 ledger 概念** |
| 变更日志 | `sync_changes`：每用户单调 `id` 游标，`GROUP BY (sync_id, entity_type)`；**无 ledger 维度** |
| 冲突 | LWW（`server_received_at` 裁决）+ `conflict_logs`；创建时 twin-merge（`mergedInto`） |
| 同步协议 | Push/Pull DTO 无 `ledgerId`；游标 = `账号 + lastChangeId`；恢复代际 = 全局 `server_meta.recovery_epoch` |
| 账号 | `users` 无 status 枚举（只有 `deleted_at` + `email_verified`）；管理员 = `admin-emails` 配置，缺省取最早注册用户 |
| 设备 | `devices.revoked_at` 已支持注销；refresh 时校验 |
| 备份 | JSON 业务备份（FORMAT_VERSION=1），恢复 = 清库重灌 + 重建 sync_changes + epoch+1，写屏障保护 |
| 接口 | `/api/v1/auth/*`、`/api/v1/sync/*`、`/api/v1/devices`、`/api/v1/account`、`/api/v1/server/health|backup|stats`、`/admin` 静态页 |
| 版本头 | `X-Api-Version: 1`、`X-Sync-Protocol-Version: 1`（`ApiVersionFilter` 强校验） |

## 1.2 客户端（Java / View 体系 / Room 2.8.4 / Retrofit / WorkManager）

| 项 | 现状 |
|---|---|
| Room | version 6；五张业务表均带 `sync_id/version/server_received_at/is_deleted/deleted_at`；**无 user_id / ledger_id** |
| 游标 | `sync_cursor` 表，主键 = `account_email`（按账号一条） |
| 同步 | `SyncCoordinator`（push 200/批 → pull 200/页）；推送时按实体当前状态构建载荷；LWW 回声保护；epoch 不匹配 → 游标清零 + 全量重推 |
| 身份 | 仅 `TokenStore`（SharedPreferences）存 `account_email`；业务仓库完全不感知用户 |
| 默认数据 | `DefaultData`：支出 10 类 + 收入 6 类 + 6 账户（建库回调与清空重置共用） |
| UI | 3 Tab（记一笔 / 图表 / 我的）；我的页分组入口；回收站在「数据管理」内 |
| 测试 | JVM 单测 + Room MigrationTest（2→…→6） |

## 1.3 结论

「一个登录账号 = 一套账」贯穿两端：服务端业务表只按 `user_id` 隔离，客户端业务表完全没有隔离维度。V3.2 的核心工程量在于：**给五张业务表加 `ledger_id`、把游标从账号级降到账本级、把权限从"登录即可"收紧为"成员 + 角色"**，并保证 V3.1 数据无损升级。

# 2. 冻结决策（承接基线第 41 章）

1. 不做多币种：单账本单主币种（默认 CNY）。
2. MEMBER 可编辑账本内全部交易，不做"仅本人交易"限制。
3. 账本删除一律软删除，普通用户无物理删除。
4. Server Owner 转移允许但需重新认证（本版本先做数据结构，交互放 V3.3 前完成）。
5. PostgreSQL dump 纳入正式灾备（本版本先完成 JSON 备份对 ledgers 的覆盖，dump 放 Phase 6）。

本计划补充的两条实现层决策：

6. **Ledger 是第 6 个同步实体**（entityType = `LEDGER`）：账本的创建/改名/删除走同步通道，保证离线可建账本；服务端在账本首次落库时初始化一次默认分类/账户（canonical syncId），客户端本地默认数据经既有 `mergedInto` 机制去重（基线第 27 章）。
7. **成员/邀请/角色不走同步通道**，走 REST（服务端唯一权威），客户端拉取展示；成员关系变化通过 `sync/status` 的 `ledgerMemberships` 感知并提示（基线第 25 章）。

# 3. 总体技术方案

## 3.1 数据模型（服务端，Flyway V4__v32_ledgers.sql）

```text
users            + status VARCHAR(16) DEFAULT 'ACTIVE'          -- ACTIVE / DISABLED
ledgers          id, user_id(owner), sync_id UNIQUE, name, description,
                 currency, is_default, is_archived, version,
                 server_received_at, is_deleted, deleted_at, created_at, updated_at
ledger_members   id, ledger_id, user_id, role(OWNER/ADMIN/MEMBER/VIEWER),
                 status(ACTIVE/REMOVED), invited_by, invited_at, accepted_at,
                 created_at, updated_at, UNIQUE(ledger_id, user_id)
ledger_invitations  id, invitation_id(UUID) UNIQUE, ledger_id, inviter_user_id,
                 invitee_email, role, status(PENDING/ACCEPTED/DECLINED/EXPIRED),
                 created_at, expires_at(7天), accepted_at
五张业务表        + ledger_id NOT NULL（回填默认账本）+ 索引；budgets 唯一键改为 (ledger_id, year, month, category_sync_id)
sync_changes     + ledger_id NOT NULL（回填）；游标语义变为 账号 + ledger + cursor
conflict_logs    + ledger_id
```

- 默认账本回填：每个用户生成 `我的账本`（sync_id = `'ledger-' || user_id || '-default'`，确定性、跨 H2/PG 可写）+ OWNER 成员资格；五表与 sync_changes 按用户回填 `ledger_id`。
- `sync_changes` 的 Pull 过滤从 `WHERE user_id=:uid` 升级为 `WHERE ledger_id IN (我的成员账本)`，同一账本的所有成员共享变更流。

## 3.2 同步协议 v2（两端同步升级）

```json
PushItem   { entityType, syncId, operation, baseVersion, ledgerId, payload }
PullRequest{ ledgerId, sinceChangeId, limit }   // ledgerId 为账本 syncId
SyncPayload + description / currency / ownerUserId（LEDGER 实体复用 name/isArchived/isDefault/isDeleted）
StatusResponse + ledgerMemberships[{ledgerSyncId, name, currency, isArchived, isDeleted,
                 isDefault, ownerUserId, role, membershipStatus, version}]
```

服务端 Push/Pull 校验链（基线 10.1）：token → 用户 status=ACTIVE → Ledger 存在（未删）→ 是成员（status=ACTIVE）→ 角色允许该操作 → 引用同账本。

- **LEDGER 实体规则**：创建 = 发起人自封 OWNER 并落成员资格；`isDefault=true` 且用户已有默认账本 → `mergedInto` 返回既有 syncId（客户端整体迁移 `ledger_id`）；改名/归档 = OWNER/ADMIN；删除（tombstone）= 仅 OWNER；已删账本上的业务写入 = `LEDGER_DELETED`。
- **角色规则**：VIEWER 一律禁写（`LEDGER_ROLE_REQUIRED`）；业务表写入需 MEMBER 及以上；账本设置需 ADMIN 及以上；删除/恢复账本、移除 ADMIN、改 ADMIN 角色 = 仅 OWNER。
- **twin-merge / 引用校验全部改为按 ledger 作用域**（分类同名同类型、账户同名、预算年月+分类）。
- 游标：客户端 `sync_cursor` 主键改为 `(account_email, ledger_sync_id)`；Pull 按账本逐个执行；recovery_epoch 仍全局，不匹配时清空全部账本游标并全量重推。

## 3.3 客户端架构改造

```text
ledger 表的 is_current 标志（迁移时落在默认账本上，切换 = 翻转标志）
        ↓
业务 DAO 全部业务查询内联子查询过滤：
        AND ledger_id = (SELECT id FROM ledger WHERE is_current = 1 LIMIT 1)
        ↓
BookkeepingRepository（所有写路径把实体对齐到当前账本；账本 CRUD / 切换入口）
        ↓
同步引擎（按账本显式：PushItem.ledgerId、按账本游标、status 成员关系对账）
```

> 实现说明：原计划用「Repository 显式接收 ledgerId + ViewModel switchMap」方案；
> 落地时改为「is_current 标志 + 查询内子查询」方案。两者隔离语义等价
> （业务查询一律限定当前账本），后者把切换账本简化为一次标志翻转，
> Room 失效跟踪自动重载全部页面，签名零改动，显著降低回归风险。
> 同步引擎不依赖该标志：它按账本 syncId 显式寻址，可跨账本读写。

- Room 6→7：建 `ledger` 表并写入默认账本（id=1，sync_id 随机 UUID，同 V3.1 实体规则）；五表加 `ledger_id`（回填默认账本）；budget 重建唯一索引；`sync_cursor` 重建为复合主键。
- 新建账本：本地落库（UUID syncId）+ 本地种子默认分类/账户 + 入队 LEDGER/分类/账户；服务端建账后 canonical 数据经 `mergedInto` 收敛，禁止出现双"现金"。
- 切换账本：`CurrentLedgerProvider.switchLedger()` → 持久化 + LiveData 翻转，所有 switchMap 查询自动重载（满足基线 6.3"无残留"）；搜索页在切换后清空结果。
- 同步循环：状态对账（memberships → 本地 ledger 表插入/角色更新/移除感知）→ push（载荷带 ledgerId）→ 按账本逐个 pull；`LEDGER_ACCESS_DENIED` → 本地标记"已被移出"并切走账本；`USER_DISABLED` → 明确提示非网络错误。

## 3.4 REST 接口（账本与成员）

```text
GET    /api/v1/ledgers                          我的账本列表（含角色/成员数）
GET    /api/v1/ledgers/{syncId}/members         成员列表（成员均可看）
POST   /api/v1/ledgers/{syncId}/invitations     邀请 {email, role}（ADMIN+，7天有效）
GET    /api/v1/invitations                      我的待处理邀请
POST   /api/v1/invitations/{invitationId}/accept
POST   /api/v1/invitations/{invitationId}/decline
DELETE /api/v1/ledgers/{syncId}/members/{userId}    移除成员（权限见 3.2）
PATCH  /api/v1/ledgers/{syncId}/members/{userId}    修改角色 {role}
POST   /api/v1/ledgers/{syncId}/restore            恢复账本（仅 OWNER）
```

新增错误码（基线第 24 章，客户端统一映射中文提示）：`LEDGER_NOT_FOUND / LEDGER_ACCESS_DENIED / LEDGER_ROLE_REQUIRED / LEDGER_DELETED / INVITATION_EXPIRED / INVITATION_ALREADY_USED / USER_DISABLED / DEVICE_REVOKED`。

# 5. 测试矩阵（本轮自动化覆盖）

服务端（H2 + Flyway 全链路）：
1. 默认账本：新用户首推 `isDefault=true` 创建成功且种子默认数据唯一；第二设备重复 claim → `mergedInto`。
2. 隔离：同用户两账本互不可见；非成员 Push/Pull → 403； Pull 只返回该账本变更。
3. 角色：VIEWER 禁写；MEMBER 可写业务不可设账本；ADMIN 可邀请不可删账本；仅 OWNER 可删/恢复。
4. 邀请：邀请→接受→成员可见可写；过期→`INVITATION_EXPIRED`；重复接受→`INVITATION_ALREADY_USED`；移除后→`LEDGER_ACCESS_DENIED` + status 通知。
5. 禁用：DISABLED 用户 login/refresh/push 全部 `USER_DISABLED`。
6. 备份：v2 备份含 ledgers/members；恢复后 epoch+1、游标失效、账本与成员关系完整。

客户端（JVM + 设备）：
1. Migration 6→7：默认账本生成、五表 ledger_id 回填、budget 唯一键、游标表重建。
2. SyncPayloadMapper：LEDGER 载荷映射、orderOf 加入 LEDGER 最先处理。
3. 人工（真机待办）：A/B 两账号三设备 → 同时记账、互拉、移除成员、删除账本、禁用账号、切换账本无残留。

# 6. 升级与兼容

1. 服务器先升级（Flyway V4 自动回填默认账本），旧 V3.1 客户端将收到 `VERSION_MISMATCH`（协议版本 1→2），需同步升级 App —— 发布说明必须写明两端一起升。
2. V3.1 → V3.2：本地 Room 6→7 自动迁移；首次同步时本地默认账本以 `isDefault=true` claim，服务端合并进回填的"我的账本"，`mergedInto` 返回后本地整体迁移 `ledger_id`，**不重生成任何业务 sync_id**（基线 5.2）。
3. v1 备份文件在 v2 服务器恢复：先按 v1 结构导入，再自动补建默认账本并回填，保证"V3.1 备份 → V3.2 服务器"路径可用。
4. 数据库迁移失败禁止继续业务写入：Flyway 失败即启动失败（现有行为保持）。

## 8.2 实现层补充决策（对基线的落地细化）

1. 账本作为第 6 个同步实体（LEDGER），创建/改名/删除走同步通道（离线可建账本），服务端建账时初始化一次默认分类/账户，与本机种子经 mergedInto 去重。
2. 成员/邀请/角色走 REST（服务端唯一权威），客户端经 `sync/status` 的 `ledgerMemberships` 对账并提示。
3. 账本级恢复走 REST（仅 OWNER）；删除走同步墓碑。
4. 注销账号时：名下账本仍有其他成员 → 所有权转移给最早加入者；无成员 → 物理清理。
5. ADMIN 只能授予低于自身角色的权限（ADMIN 的任免属于 OWNER）。
