# 极简记账 App V3 产品设计与开发基线

> 版本：V3.0
>
> 产品定位：个人自用 / 学习项目
>
> 核心主题：**本地优先 + 家庭自建服务器 + 可选云端同步 + 多设备一致性**
>
> 基线状态：正式开发基线
>
> 上一版本基础：V2.1（体验优化 + 数据一致性 + 长期稳定性）
>
> 本文用于 V3 开发前的产品、架构、数据模型、同步协议、UI、验收标准统一。未在本文另行覆盖的 V1/V2/V2.1 行为继续沿用既有基线。

---

## 1. V3 产品目标

V3 不再只是“单机记账工具”，而是在保持本地记账体验的前提下，增加一个**可选的跨设备数据同步体系**。

V3 的核心目标：

1. 用户可以使用邮箱 + 密码注册和登录。
2. 注册后必须完成邮箱验证。
3. 用户登录后，可以让多台手机/设备共享同一套账务数据。
4. 数据默认仍以手机本地数据库为主要工作数据源，离线时完整可用。
5. 家庭电脑作为自建服务器，运行 Spring Boot + PostgreSQL，并通过 Docker Compose 管理。
6. “云端同步”是一个用户可以主动控制的开关，而不是本地记账的前置条件。
7. 家庭电脑关机、没有网络、登录失效、Refresh Token 失效，都不能阻塞本地记账。
8. 服务器恢复、网络恢复、重新登录后，可以继续同步未完成的数据。
9. 多设备同时修改同一条数据时，采用已冻结的 LWW + Soft Delete + conflict log 策略。
10. V3 首要目标是形成一套稳定、可验证、可长期运行的同步基础设施，不扩张到 AI、OCR、家庭共享、投资等大型方向。

## 2. 产品原则

### 2.1 本地优先

> **本地数据库负责实时工作，同步机制负责后台数据交换。**

用户的记账、查看图表、账户管理、预算管理等核心功能，不依赖家庭服务器在线。

### 2.2 登录不等于本地使用权限

> **登录用于云同步，不用于本地记账权限。**

以下任一情况都不能禁用本地功能：

- 没有网络
- Access Token 失效
- Refresh Token 失效
- 家庭电脑服务器关机
- 家庭服务器暂时不可访问
- 自动同步失败

### 2.3 同步可控

“我的”页面增加：

> **云端同步 [开 / 关]**

关闭时只暂停本设备的云端同步，不退出账号、不删除云端数据、不删除本地数据。

### 2.4 同步不打断记账

同步过程不能锁定交易、账户、预算或其他本地业务对象。用户可以在同步期间继续新增、修改、删除账单。

### 2.5 服务器负责一致性裁决

客户端不自行猜测最终冲突结果。涉及跨设备冲突时，以服务器最终裁决结果为准，并将冲突写入服务器 conflict log。

## 5. 账号与认证体系

### 5.1 注册

采用：

> **邮箱 + 密码注册，注册后必须验证邮箱。**

注册成功后：

1. 创建服务器账号。
2. 发送验证邮件。
3. 未验证邮箱时不视为完整激活状态。
4. 用户验证邮箱后才可完成正常云同步能力开通。

### 5.2 登录

登录凭据：

- Email
- Password

认证方式：

- Access Token：短期有效
- Refresh Token：长期有效

Access Token 用于普通 API 请求。

Refresh Token 用于在 Access Token 失效后获取新的 Access Token。

### 5.3 Refresh Token

每台设备使用独立 Refresh Token。

服务器保存每个设备对应的 Refresh Token 状态，而不是所有设备共用一个 Refresh Token。

支持：

- 单设备退出登录
- 退出当前设备
- 全部设备退出
- 服务端主动吊销指定设备 Token
- Refresh Token 轮换

### 5.4 密码安全

服务端只保存密码哈希，不保存明文密码。

推荐使用成熟的密码哈希算法和 Spring Security 的标准密码校验能力。

## 6. 家庭自建服务器

### 6.1 部署定位

V3 不以 VPS 为默认部署环境。

第一阶段：

> **本地开发 → 家庭电脑运行正式测试服务器**

家庭电脑作为用户自己的长期服务器。

### 6.2 技术栈

服务器端：

- Linux
- Docker Compose
- Spring Boot
- PostgreSQL

建议组件结构：

```text
家庭电脑
└── Docker Compose
    ├── reverse-proxy / HTTPS 入口
    ├── Spring Boot API
    └── PostgreSQL
```

开发阶段可以先在开发电脑本机运行 PostgreSQL / Spring Boot，数据库结构稳定后再部署到家庭电脑。

### 6.3 服务器离线行为

家庭电脑关机时：

> **手机 App 不受影响。**

表现为：

```text
手机本地记账      正常
图表              正常
账户              正常
预算              正常
搜索              正常
本地备份/恢复     正常
云端同步          暂停
```

家庭电脑重新开机后，如果手机有网络且“云端同步”开启：

> 自动恢复同步。

### 6.4 网络访问

服务器网络接入、安全访问、HTTPS、动态公网地址 / 域名、家庭路由器配置等作为部署层问题处理。

原则：

> **不因为家庭宽带环境不稳定而牺牲本地优先体验。**

V3 不要求手机必须一直能访问家庭服务器。

## 7. 云端同步开关

### 7.1 入口

「我的」页面增加：

```text
云端同步                    [开关]
```

建议同时显示状态摘要：

开启：

```text
已开启 · 最近同步：刚刚
```

服务器暂时不可用：

```text
已开启 · 服务器暂不可用
```

关闭：

```text
已关闭 · 仅使用本地数据
```

### 7.2 开启

打开开关后，执行一次初始化检查：

- 当前是否已登录
- 邮箱是否已验证
- Token 是否有效
- 家庭服务器是否可访问
- 本地是否存在待同步数据
- 云端是否已有数据

满足条件后开始增量双向同步。

### 7.3 关闭

关闭后：

- 停止自动云端同步
- 停止后台同步任务
- 不删除本地数据
- 不删除服务器数据
- 不退出登录
- 不产生主动网络同步请求

关闭期间发生的本地新增、修改、删除继续记录同步变更信息，重新打开同步后再处理。

### 7.4 开关语义

> “云端同步”控制的是**本设备的数据同步行为**，不是账号是否存在，也不是本地功能是否可用。

## 8. 首次登录与首次同步

### 8.1 首次登录流程

用户首次完成登录后，服务器判断云端是否已有该账号的数据。

分两种情况：

#### 情况 A：云端为空

> **本地数据初始化云端。**

同步前展示本地数据统计，例如：

- 账单：N 笔
- 账户：N 个
- 分类：N 个
- 预算：N 条
- 周期账单：N 条

用户确认后上传并初始化云端。

#### 情况 B：云端已有数据

> **本地与云端双向合并。**

同步前展示双方统计，例如：

```text
本地
账单：120 笔
账户：6 个
分类：18 个

云端
账单：95 笔
账户：5 个
分类：16 个
```

然后明确提示：

> “首次同步将合并本地与云端数据，请确认后继续。”

用户确认后才执行首次双向合并。

### 8.2 首次同步原则

第一次同步不是简单的“云端覆盖本地”或“本地覆盖云端”。

对于双方都存在的同一 `syncId`：

- 比较版本 / 变更信息
- 根据既定冲突规则确定最终版本
- 必要时记录 conflict log

对于仅存在本地的数据：上传云端。

对于仅存在云端的数据：下载本地。

## 9. 同步触发策略

已冻结的同步触发规则：

### 9.1 进入 App

进入 App 时执行一次增量双向同步。

### 9.2 回到前台

App 从后台回到前台时执行一次增量双向同步。

### 9.3 本地数据变化

本地新增 / 修改 / 删除数据后启动防抖计时：

> **本地数据停止变化 3 秒后触发同步。**

连续操作时不断重置计时器，避免一次操作产生大量网络请求。

### 9.4 手动立即同步

同步中心提供：

> **立即同步**

点击后：

- 不等待 3 秒防抖
- 直接启动增量双向同步
- 如果已有同步任务正在运行，则不重复创建任务，而是复用当前任务

### 9.5 网络恢复

检测到网络恢复后：

> **立即触发一次增量双向同步，不等待原有重试倒计时。**

### 9.6 家庭服务器恢复

当家庭电脑从关机状态恢复并重新可访问时，按照普通网络恢复 / 服务可用恢复逻辑触发同步。

---

## 10. 同步失败与重试

### 10.1 指数退避

同步失败采用指数退避，最长间隔 30 分钟。

建议默认序列：

```text
第 1 次失败 → 5 秒
第 2 次失败 → 15 秒
第 3 次失败 → 30 秒
第 4 次失败 → 1 分钟
后续逐步增加
最大间隔 → 30 分钟
```

### 10.2 网络恢复优先

如果在退避等待期间网络恢复：

> 立即重试，不等待剩余倒计时。

### 10.3 手动同步优先

用户点击“立即同步”时：

> 允许立即触发，不受当前退避计时限制；若已有同步任务，则复用当前任务。

### 10.4 App 重启

App 重启后，未完成的同步任务和待上传变更不能丢失。

同步队列使用本地持久化，而不是仅存在内存中。

---

## 11. 同步期间的本地操作

同步过程中：

> **完全允许继续新增、修改、删除本地账单。**

示例：

```text
本地存在 10 条待同步变更
        ↓
开始同步
        ↓
用户又新增 2 条账单
        ↓
当前同步继续处理原有批次
        ↓
新产生的 2 条进入后续同步批次
```

同步任务不能通过数据库锁住整个业务层，也不能阻止交易编辑页面正常保存。

---

## 12. 同步批次与并发控制

### 12.1 单设备单同步任务

同一设备同一时刻只允许一个有效同步流程。

多个触发源同时到达时：

```text
进入 App ┐
回到前台 ├──→ SyncCoordinator ──→ 单一同步任务
本地变更 ┤
手动同步 ┘
```

### 12.2 快照失效

同步任务获取待上传数据后，如果用户在同步过程中再次修改同一条数据：

> **旧同步快照立即失效，不得把旧数据覆盖回本地。**

本地最新版本进入后续同步处理。

---

## 13. 跨设备数据标识

V3 不允许仅依赖 SQLite 自增 ID 作为跨设备数据身份。

每个可同步实体增加稳定的：

> **`syncId`：UUID / UUID-like 全局唯一业务标识。**

本地数据库仍可以保留自己的 SQLite `id` 作为本地存储标识，但：

- 本地 `id`：本机数据库内部使用
- `syncId`：跨设备、云端、同步协议使用

适用实体至少包括：

- Category
- Account
- Transaction
- Budget
- RecurringTransaction
- UserSettings（如未来进入跨设备同步范围）

---

## 14. 同步元数据模型

所有可同步实体建议统一具备以下同步元数据：

```text
sync_id
version
base_version（仅同步请求/变更上下文，必要时不落实体）
updated_at
server_received_at
is_deleted
```

其中：

### `sync_id`

跨设备稳定唯一身份。

### `version`

服务器维护的整数版本号。

规则：

> **每条可同步数据都有独立 `version`；服务器每次接受该条数据的有效修改时，`version + 1`。**

### `updated_at`

客户端实际业务修改时间。

> `updated_at` 用于记录业务事实，但**不作为跨设备最终 LWW 裁决依据**。

### `server_received_at`

服务器接收到有效修改的服务端时间，用于跨设备最终排序。

### `is_deleted`

Soft Delete 标记。

---

## 15. 乐观并发控制

客户端上传时必须携带：

> **`baseVersion`：该客户端修改前所看到的服务器版本。**

### 15.1 无冲突

```text
客户端 baseVersion = 5
服务器当前 version = 5
```

服务器接受：

```text
写入数据
version = 6
```

并返回最终版本给客户端。

### 15.2 发生并发修改

```text
客户端 baseVersion = 5
服务器当前 version = 6
```

说明客户端基于旧版本做了修改。

此时：

> **不允许旧版本直接覆盖服务器新版本。**

进入冲突处理流程。

---

## 16. LWW 冲突策略

已经冻结：

> **普通字段采用 LWW（最后修改者获胜）；删除采用 Soft Delete；发生冲突时服务器记录 conflict log，但不弹窗阻塞用户。**

### 16.1 最终裁决依据

跨设备最终裁决：

> **服务器接收时间 + 数据版本号。**

客户端自己的 `updated_at` 不参与跨设备最终胜负判断。

### 16.2 冲突后客户端行为

服务器完成裁决后：

1. 返回该条数据的最终胜出版本。
2. 返回服务器最终 `version`。
3. 客户端接受服务器最终版本。
4. 本地更新对应同步元数据。
5. 冲突记录留在服务器 conflict log 中。

客户端不得根据自己的猜测继续覆盖服务器结果。

### 16.3 冲突不打扰用户

普通冲突不弹模态窗阻塞记账。

必要时只在同步中心展示：

```text
最近同步：完成
发生冲突：1 条
```

冲突详细审计信息留在服务器侧，V3 不要求做复杂的用户端冲突编辑器。

## 17. Soft Delete

删除统一采用 Soft Delete。

删除一条交易/账户/分类等可同步实体时：

```text
is_deleted = true
version + 1
```

而不是马上物理删除。

### 17.1 原因

必须让“删除”本身成为可同步事件，否则：

```text
设备 A 删除
设备 B 仍有旧数据
A 物理删除后服务器查不到
B 无法知道自己应该删除
```

Soft Delete 可以保证删除信息跨设备传播。

### 17.2 本地 UI

普通列表默认不显示已删除数据。

## 22. 双向增量同步流程

标准同步流程：

```text
1. 获取有效 Access Token
        ↓
2. 检查服务器可用性
        ↓
3. Push 本地待同步变更
        ↓
4. 服务器进行 baseVersion 校验
        ↓
5. 无冲突 → 写入并 version + 1
        ↓
6. 有冲突 → LWW 裁决 + conflict log
        ↓
7. 返回 Push 结果
        ↓
8. Pull 服务器自上次游标后的变更
        ↓
9. 客户端应用服务器最终版本
        ↓
10. 更新本地 sync cursor
        ↓
11. 检查同步过程中是否产生新的本地变更
        ↓
12. 有则继续下一批，没有则完成
```

### 22.1 顺序

V3 默认采用：

> **先 Push，再 Pull。**

原因：可以先把本地用户刚刚产生的变化提交到服务器，再获取服务器最终状态。

最终的实现必须保证：

> **旧同步快照不能覆盖同步期间产生的新本地修改。**


- 同步成功后清理已完成队列项。

## 24. 登录失效 / Refresh Token 失效

规则已经冻结：

> **登录失效 / Refresh Token 失效 / 没有网络，都不影响本地 App 使用。**

### 24.1 Access Token 失效

自动尝试 Refresh Token。

### 24.2 Refresh Token 仍有效

获取新的 Access Token，继续同步。

### 24.3 Refresh Token 失效

同步状态进入：

> `AUTH_REQUIRED`

同时：

- 本地记账继续正常运行
- 图表继续正常运行
- 账户继续正常运行
- 预算继续正常运行
- 同步队列继续保留
- 用户重新登录后恢复同步

### 24.4 不允许的数据行为

Refresh Token 失效不能导致：

- 清空 Room
- 删除本地账单
- 强制退出到不可使用状态
- 禁止进入 Record / Chart / Mine

## 30. 安全基线

由于家庭服务器可能通过公网访问，V3 必须把安全作为 P0 基础设施。

最低要求：

- HTTPS
- 密码哈希存储
- Refresh Token 可吊销
- Refresh Token 不明文长期暴露给日志
- 服务端 API 身份鉴权
- 用户数据严格按 `user_id` 隔离
- PostgreSQL 不直接暴露公网
- 管理端口不直接暴露公网
- API 具备基础请求限流 / 防暴力破解机制
- 敏感日志不记录密码、完整 Token
- 邮箱验证 Token 有有效期且单次使用

家庭电脑部署时，数据库服务原则上只允许内部 Docker 网络访问。

## 31. “用户数据隔离”原则

即使 V3 当前是纯自己使用 / 学习项目，服务端仍按“一个用户一个数据空间”设计。


## 32. 数据删除与账号注销

账号注销属于高风险操作，需要明确区分：

### 32.1 退出登录

只影响当前设备登录状态。

本地业务数据保留。

### 32.2 退出全部设备

撤销该账号所有有效 Refresh Token / Session。

云端数据不删除。

### 32.3 删除账号

属于破坏性操作，需要二次确认。

建议流程：

```text
用户确认删除账号
   ↓
身份再次确认
   ↓
服务器标记账号进入删除流程
   ↓
删除/匿名化其云端数据
   ↓
撤销全部设备
```

本地数据是否同时删除不作为隐式行为，必须单独提示。

## 36. 账户 / 交易同步注意事项

V2 已定义：

- 收入/支出交易必须有账户
- 转账必须有转出账户和转入账户，且两者不同
- 转账不写分类
- 转账不计入收支统计
- 账户余额由初始余额和资金流计算

V3 同步不能改变这些业务规则，只负责在设备与服务器之间传输这些状态。

因此：

> **同步层不是账务层。**

同步服务不应自行重新定义“收入/支出/转账”的业务口径。

V2 已明确余额公式、转账排除统计和账户缓存校验逻辑。 fileciteturn5file0L18-L26

## 37. 账户初始余额的历史基线

V2 已识别出“历史账单归属账户后，初始余额可能与历史资金流重复计算”的潜在风险。

V3 开发同步前必须保持现有 V2.1 的既定语义，并在正式实现跨设备同步前明确账户 `initial_balance` 的基准日期/起点。

同步本身不得：

- 自动修改用户的初始余额
- 因多设备合并而重复计算历史交易
- 将同一历史交易复制到多个账户

如果需要改变初始余额语义，应单独增加产品决策，不在同步层隐式修正。

## 38. 分类、账户和预算同步规则

## 39. 周期账单同步

周期账单是规则数据，不应把“下一次待生成日期”简单视为唯一业务身份。

跨设备同步时：

- 同步规则本身
- 同步 `anchor_day_of_month`
- 同步启用状态
- 同步开始/结束日期
- 同步 `next_run_date`

当多设备同时修改周期规则时，仍按普通实体的版本冲突策略处理。

V2.1 已修复 1/31 → 2/28 → 3/28 的月末漂移，并以 `start_date` 的原始日作为锚点回填依据。 fileciteturn5file1L179-L183

## 40. CSV / 本地备份与云同步的关系

现有 V2/V2.1 的 CSV 导入导出、本地 JSON 备份恢复继续保留。

需要明确：

> **本地备份 ≠ 云端同步。**

CSV：适合用户交换数据、导出分析。

本地 JSON 备份：适合恢复本机数据。

云端同步：适合跨设备持续保持状态一致。

三者的数据协议和版本号必须分开管理。

建议至少区分：

## 41. 版本兼容原则

V3 开始明确区分：

### DB Schema Version

Room Migration 使用。

### Backup Schema Version

本地备份恢复使用。

### API Version

客户端与家庭服务器接口兼容使用。

### Sync Protocol Version

同步数据协议兼容使用。

不能将四者混为同一个“version”。

实体 `version` 是**业务数据版本号**，也不等于数据库 schema version。

## 49. V3 最重要的架构结论

本版本以下原则视为不可随意破坏的基线：

1. **本地优先。**
2. **服务器离线不能阻塞本地记账。**
3. **云端同步由“我的”中的开关控制。**
4. **关闭同步不是退出账号，不删除数据。**
5. **邮箱 + 密码登录，注册后必须验证邮箱。**
6. **JWT Access Token + Refresh Token。**
7. **每设备独立 Refresh Token。**
8. **不限制设备数量。**
9. **首次同步前必须显示数据统计并要求用户确认。**
10. **云端为空 → 本地初始化云端；云端有数据 → 双向合并。**
11. **App 启动、回前台、本地变更 3 秒后、手动立即同步都可以触发同步。**
12. **失败采用指数退避，最长 30 分钟。**
13. **网络恢复立即同步。**
14. **同步过程中允许继续记账。**
15. **旧同步快照不能覆盖新的本地修改。**
16. **普通字段采用 LWW。**
17. **删除采用 Soft Delete。**
18. **服务器记录 conflict log。**
19. **每条可同步数据独立维护整数 `version`。**
20. **客户端上传必须携带 `baseVersion`。**
21. **服务器负责最终冲突裁决，并返回最终版本。**
22. **跨设备最终裁决使用服务端接收时间 + 数据版本号，而不是客户端系统时间。**
23. **家庭电脑采用 Linux + Docker Compose + Spring Boot + PostgreSQL。**
24. **数据库、备份、API、同步协议的版本号分开管理。**

## 52. 结论

V3 的核心不是把手机变成“必须联网的客户端”，而是建立一个：

> **即使家庭服务器完全关闭，手机也依然是一款完整可用的记账 App；服务器在线时，则自动把多个设备的数据保持一致。**

最终形态：

**手机本地 Room = 实时工作区**  
**家庭电脑 PostgreSQL = 自建云端数据中心**  
**Spring Boot = 云端业务与同步服务**  
**WorkManager + SyncCoordinator = 移动端同步引擎**  
**SyncId + Version + BaseVersion = 一致性基础**  
**LWW + Soft Delete + Conflict Log = 冲突处理机制**

这套结构既保留极简记账 App 的“打开就能记”，又为后续多设备、数据安全和更复杂的个人财务能力留下稳定基础。
