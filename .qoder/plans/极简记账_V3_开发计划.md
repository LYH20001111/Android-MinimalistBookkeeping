## 实施备注（关键落地决策与基线解释）

以下是对基线中留有解释空间之处的落地决策；均不违背基线第 49 章的 24 条不可破坏原则。

1. **LWW「最后」的定义 = 服务器接收顺序**（基线 16.1「服务器接收时间 + 数据版本号」的落地）：
   服务器串行处理 Push，后接收到的写入即为「最后修改」，冲突时胜出并 `version + 1`；
   被覆盖方完整记录进 `conflict_logs`（含双方 payload 摘要与 winner 字段）。
   「不允许旧版本直接覆盖服务器新版本」（基线 15.2）落实为：`baseVersion` 不匹配的写入
   **必须经过冲突流程**（记录 + 返回最终胜出版本），不允许静默覆盖；客户端无条件接受
   服务器返回的最终版本。选择服务器接收序而非客户端 `updated_at` 做逻辑时钟，
   正是为规避基线明令禁止的「客户端系统时间参与裁决」与多设备时钟偏差问题。
   同批次内接收时间相同（同毫秒）时以 `version` 高者胜。
2. **服务端引用列统一存 `sync_id`（TEXT）**，不建跨业务表外键，由 Service 层校验
   （引用必须属于同一 `user_id` 且存在；软删行仍存在故可引用）。
   避免「先推账单、后推账户」的顺序问题演变为数据库层约束失败；Push 服务端按
   分类 → 账户 → 交易/预算/周期 的分组顺序处理，进一步降低悬挂引用概率。
3. **Refresh Token 采用不透明随机串（256-bit）+ 服务端 SHA-256 哈希存储**，设备绑定、
   旋转发放（每次 refresh 换新），撤销 = 置 `revoked_at`。Access Token 采用 JWT（30 分钟）。
   两者均不进日志（基线 30、45 章）。
4. **邮箱验证 Token**：SHA-256 哈希落库、24 小时有效、单次使用。邮件通过 SMTP 发送
   （`spring-boot-starter-mail`，环境变量配置）；开发/无 SMTP 环境下验证链接打印到服务端日志。
   **登录不要求已验证**；`email_verified=false` 时登录成功但所有 Sync API 返回
   `EMAIL_NOT_VERIFIED`，客户端同步状态显示「需要验证邮箱」，本地功能不受任何影响。
5. **本地同步元数据列**：5 个可同步实体（category/account/transactions/budget/
   recurring_transaction）各增加 `sync_id`（TEXT NOT NULL DEFAULT ''，迁移时为存量行生成 UUID）、
   `version`（INTEGER NOT NULL DEFAULT 0，含义 = 客户端最后一次从服务器确认的版本，0 = 从未同步）、
   `server_received_at`（INTEGER NOT NULL DEFAULT 0）、`is_deleted`（INTEGER NOT NULL DEFAULT 0）。
   本地自增 `id` 保留原职责；`user_settings` 不进入 V3 同步范围（基线 13 章）。
6. **同步队列合并与快照失效**（基线 12.2、23 章）：队列按 `(entity_type, sync_id)` 合并——
   非同步运行期间的新变更直接覆盖同键队列行（保留最早 `created_at`）；同步运行期间产生的
   变更写入新队列行，不污染在途批次快照。Push ack 采用**双重护栏**：仅当本地实体
   `version == 推送时快照 baseVersion` **且** 当前实体内容与快照内容一致时，才回写
   服务器最终版本并清理队列行；否则丢弃 ack（服务器已接受的数据即为合法历史版本），
   本地最新状态保留在队列中进入下一轮同步。这样「同步中修改」永远不被旧快照覆盖。
7. **Pull 应用规则**：仅当 `服务器 version > 本地 version` 时应用服务器载荷（本机刚 Push
   的回显因版本相等而自然跳过）；相等或更小则跳过并计入诊断。应用后触发账户余额重算校验
   （继承 V2「缓存不是唯一真值」）。
8. **sync cursor 按账号隔离**（`sync_cursor` 表以账号 email 为主键）：退出登录不清数据、
   换账号登录不串游标；同一账号重新登录后从原游标继续增量拉取。
9. **Soft Delete 替换物理删除的范围**：交易删除、未引用分类删除、未引用账户删除、
   周期账单删除一律改为 `is_deleted = true + version + 1`；**被引用的分类/账户仍禁止删除**
   （账户走归档，语义不变，V2 规则「同步层不是账务层」）。普通列表查询全部过滤
   `is_deleted = 0`；本地备份 JSON 增补 `syncId`（Backup Schema Version 3→5），恢复时
   保留身份但 `version/server_received_at` 归零并入队全量重推，由服务器 LWW 收敛。
10. **服务器地址**为用户配置项（同步中心内设置，如 `http://192.168.1.10:8080`），
    存 SharedPreferences。Android 侧允许明文 HTTP（家庭局域网场景），部署侧由
    docker-compose 附带的 Caddy 反向代理提供自动 HTTPS（基线 6.4 将网络接入列为部署层问题；
    安全基线的 HTTPS 要求在部署 compose 中落地）。
11. **API Version = 1、Sync Protocol Version = 1**：客户端请求头 `X-Api-Version` /
    `X-Sync-Protocol-Version`，服务器不匹配时返回明确错误码；四类版本号
    （DB Schema / Backup / API / Sync Protocol）分开管理（基线 40、41 章）。
12. **服务端构建**：`server/` 独立 Gradle 工程（Kotlin DSL + Spring Boot 3.5 + Java 17 +
    JPA + Flyway + PostgreSQL），docker-compose 编排 `postgres` + `api`（+ 可选 `caddy`）。
    开发期可在本机直跑 PostgreSQL 容器 + Gradle bootRun。
13. **WorkManager 角色**（基线 28 章）：失败重试的持久化调度（带指数退避延迟的
    one-shot + 网络约束）与「进程被杀后仍能续传」的兜底；3 秒防抖、前后台切换、
    网络恢复回调等前台路径由 SyncCoordinator 进程内直接调度（低延迟）。
    同步真值始终以 Room 为准。
14. **账号注销**：客户端二次确认（重新输入密码）→ 服务器删除云端业务数据 + 匿名化
    users 行 + 撤销全部设备 → 客户端退出登录并单独询问是否同时清空本地数据
    （基线 32.3，本地清理不是隐式行为）。

## 1. 现状盘点（计划编制时对 V2.1 代码的实测结论）

| 领域 | 现状 | 与基线差距 |
|---|---|---|
| 数据库 | `AppDatabase` version 4，`MIGRATION_1_2/2_3/3_4` 集中管理，外键 RESTRICT，schema 导出至 `app/schemas` | 需 v4→v5：5 表加同步元数据 + 新建 `sync_change_queue` / `sync_cursor` / `sync_state` |
| 实体 | 5 个可同步实体 + `user_settings`；交易含 `account_id/transfer_account_id` 可空外键；budget 有 `(year,month,category_id)` 唯一索引 | 实体需加 4 个同步元数据字段 |
| 删除语义 | 交易/分类（未引用）物理删除；账户未引用物理删除、被引用归档 | 改 Soft Delete（备注 9） |
| 网络 | Manifest **刻意不声明 INTERNET 权限**（V1 断网可用的构建级保证） | 需加 `INTERNET` + `ACCESS_NETWORK_STATE`；断网可用由「本地优先」架构继续保证 |
| Repository | 单一 `BookkeepingRepository`（943 行），全部写路径集中，IoExec 单线程池 | 所有写路径需挂钩：插入分配 `syncId`、写后入队、删除改软删 |
| 备份 | `BackupSerializer`（Backup Schema Version 4）+ `RestoreUseCase.replaceAllData` | 备份增补 `syncId`，恢复重置版本并入队 |
| 架构分层 | ui / domain / data 三层，无 remote/sync 层；组合根在 `BookkeepingApp` | 按基线 27 章新增 `data.remote` + `sync` 包，UI/ViewModel 不触碰 HTTP |
| 认证 | 无任何账号体系（Mine 页无登录入口） | 新增 auth UI + Token 管理 |
| 服务器 | 无 | 全新 Spring Boot 工程 + PostgreSQL + Docker Compose |
| 测试 | JVM 单测 193 个；仪器测试 MigrationTest、AccountBalanceConsistencyTest | 补同步协议纯函数单测 + Migration v4→v5 仪器测试 |
| 工具链 | Gradle 9.3.1（腾讯镜像），JDK 17/21，AGP 9.1.1 | 服务器工程复用同版本 Gradle |

## 3. 同步协议（冻结稿）

```
请求头：Authorization: Bearer <accessToken>
        X-Api-Version: 1
        X-Sync-Protocol-Version: 1
        X-Device-Id: <deviceId>

POST /api/v1/sync/push
  req : { changes: [ { entityType, syncId, operation(UPSERT|DELETE),
                       baseVersion, clientUpdatedAt, payload{...} } ] }
  resp: { results: [ { entityType, syncId, accepted, conflicted, version,
                       serverReceivedAt, payload } ], serverTime }
  // payload 内引用字段（categorySyncId/accountSyncId/transferAccountSyncId）均为 syncId
  // conflicted=true 表示发生了 LWW 覆盖，payload 为服务器最终胜出状态

POST /api/v1/sync/pull
  req : { sinceChangeId, limit }
  resp: { changes: [ { changeId, entityType, syncId, operation, version,
                       serverReceivedAt, payload } ], lastChangeId, hasMore }

GET  /api/v1/sync/status          → { serverTime, emailVerified }
GET  /api/v1/sync/bootstrap/summary → { hasCloudData, counts{category,account,transaction,budget,recurring} }
```

错误码（用户不可见原文，客户端统一转译）：`AUTH_REQUIRED`(401) / `EMAIL_NOT_VERIFIED`(403) /
`RATE_LIMITED`(429) / `VALIDATION_ERROR`(400) / `MISSING_REFERENCE`(409) / `SERVER_ERROR`(500)。

## 4. 风险与既知限制

| # | 风险/限制 | 处置 |
|---|---|---|
| 1 | 本地备份恢复后与云端 LWW 全量冲突（按 syncId 逐条记录 conflict log） | 备份含 syncId 保证身份连续；冲突日志可审计；可接受的收敛代价 |
| 2 | 清空本地数据后云端数据会随下次同步回流 | 「数据管理-清空」文案明示仅清本地；云端清理走账号注销 |
| 3 | 同一毫秒内同实体两次本地写 + 同步竞态 | ack 双重护栏（版本 + 内容一致）保证不丢最新本地状态 |
| 4 | 服务器 change log 无限增长 | V3 不做 compaction；change log 支持按用户清理（部署侧定期任务），游标重置 = 重新 bootstrap |
| 5 | 家庭服务器无固定域名/证书 | Caddy compose 提供自动 HTTPS 路径；局域网明文为开发期折衷（备注 10） |
| 6 | 仪器测试需真机/模拟器 | CI 无设备时以 JVM 单测 + 构建绿为门禁，迁移测试在真机执行 |

## 6. 完成备注（开发过程中的实际偏离与发现）

1. **服务端 LWW 补全了 DELETE 分支**：集成测试 `softDelete_propagates_via_pull`
   揪出初版缺陷——对已存在行执行 DELETE 时误走了「应用业务字段」路径（payload 为 null
   导致 NPE）。修正为：DELETE 只置软删位（`applyDeleteOrFields`），UPSERT 才应用字段。
2. **`sync_state` 的 `status` / `last_error` 为可空列**：实体字段未加 `@NonNull`，
   Room 迁移校验（真机 MigrationTest）要求列可空；默认值由字段初始化
   `= "IDLE"` 保证，迁移 SQL 已对齐。
3. **服务端 budgets 表列名 `budget_year` / `budget_month`**：`YEAR` / `MONTH` 是
   H2 保留字，为让「同一份 Flyway SQL 同时服务 PostgreSQL（生产）与 H2（集成测试）」
   而改名；协议 JSON 字段名（year/month）不变，客户端无感知。V1 基线 SQL 同步改写为
   标准 SQL（IDENTITY / TIMESTAMP WITH TIME ZONE / CURRENT_TIMESTAMP），两库通用。
4. **回调契约扩展**：`util/Callback` 增加 `default onError(Exception)`，默认回退为
   `onResult(null)`，V1/V2 全部既有调用点行为不变；认证 / 同步路径覆写以区分错误。
5. **SyncCoordinator 事务改为内联**：协调器运行在仓库单线程 IO 执行器上，
   事务必须用 `database.runInTransaction` 同步执行；若经 `runOnIo` 异步排队，
   ack 判断会读到排队前的旧状态（开发期自查发现并修正）。
6. **修复 V2.1 遗留测试失败**（非 V3 引入）：commit a29f7a7 按产品决策停用
   「最近使用」区块后，`SearchActivitySmokeTest.pickerAdapters_bindHeaderAndItemRows`
   仍断言 4 行；已按当前行为（伪项 + 数据行 = 2 行）修正断言。
7. **真机验证**：本次开发在已连接真机（HUAWEI ANG-AN00）上执行了
   `connectedDebugAndroidTest`，V2.1 余额一致性 / 搜索冒烟 / V3 迁移测试全部通过。
8. **游标防回退**：Pull 遇到悬挂引用（引用方尚未同步）时游标停留在最后一条
   完整应用的位置，下轮同步从那里续拉；引用方到位后自然推进。

9. **真机联调期修复 JwtAuthFilter 缺陷**：过滤器原先只写自定义 ThreadLocal，
   未把认证信息写入 Spring `SecurityContext`，导致 `.authenticated()` 规则
   对所有携带合法 Token 的请求返回 403（集成测试直连控制器未暴露该层）。
   已补 `SecurityContextHolder` 写入并清理；本机 H2 端到端冒烟
   （注册 → 邮箱验证 → 登录 → Push → Pull → bootstrap 统计）全部打通。
10. **本机运行形态**：开发机无 Docker / PostgreSQL，`server/run-local.bat`
    以内嵌 H2（PostgreSQL 兼容模式）+ 文件持久化启动服务器，Flyway 同一套
    V1/V2 迁移直接可用；`build.gradle.kts` 已把 H2 驱动加入 runtimeOnly。
    家庭电脑正式部署仍按 server/README 使用 Docker Compose + PostgreSQL。
    真机（192.168.0.11）已安装 3.0.0 debug APK，与服务器（192.168.0.2:8080）
    同网段互通（ping 0% 丢包；App 层连通性随首次登录验证，需放行防火墙入站 8080）。

11. **真机联调期修复两处客户端缺陷**（首次多设备实测发现）：
    ① 正常记账后自动同步不触发——`enqueueSync` 只入队、漏发
    `notifyPendingChanges()`，3 秒防抖链路从未被启动（仅备份恢复路径发了通知）；
    已在入队后补发通知（主线程 → 防抖 → IO 队列，天然在写事务提交后执行）。
    ② 登录 / 注册失败时界面无任何反馈——错误文案写入默认 `gone` 的
    TextView 且从未设回可见；已改为有内容即显示。两者修复后
    202 个 JVM 单测回归全绿，3.0.0 APK 已重装真机。

12. **真机联调期修复认证主线程网络缺陷**（第二台设备实测「未知错误」暴露）：
    `AuthRepository.run` 原在调用线程（主线程）同步执行 `call.execute()`，
    必然抛 `NetworkOnMainThreadException` 并被兜底为「未知错误」——这同时解释了
    手机 1「登录后无反应」（当时错误提示还不可见）与手机 2「未知错误」。
    已改为专用单线程执行器执行 HTTP、回调统一回主线程；手机 1 的
    `sync_auth.xml` 仅含 device_id 证实其从未登录成功，服务器日志中亦无
    真实账号注册记录。修复后构建与 202 个 JVM 单测全绿，APK 已重装真机。

13. **触发策略补充（用户联调期提出，基线第 9 章的修订）**：基线的触发源全部是
    本机事件（启动/回前台/本地变更/手动/网络恢复），服务器无推送通道——
    多设备场景下「另一台设备写入后本机不会被动收到」。为满足两台手机
    近实时收敛的体验预期，经产品确认补充两个触发源：
    ① 前台轻量轮询（App 可见期间每 30 秒增量拉取一次，仅前台运行）；
    ② WorkManager 周期同步（每 15 分钟，网络约束，后台/被杀兜底）。
    本轮多设备实测（手机 2 写入 → 手机 1 手动可同步）暴露了该体验缺口，
    修订记录于此；其余冻结条款不变。

14. **多设备重名去重（真机多设备实测发现的设计缺口，已完成修复）**：两台设备各自
    初始化的默认分类/账户名字相同但 syncId 不同，首次合并时被服务器当作不同实体，
    造成分类/账户成对重复。修复分三层：
    ① 服务端创建路径防重（治本）——Push 遇到同用户已有同名同类型分类 / 同名账户 /
    同（年，月，分类）预算时不再新建，应答携带 `mergedInto=已有syncId`
    （Sync Protocol v1 的可空加字段，向后兼容）；
    ② 客户端应答处理——`applyMergedInto` 把本地行身份重映射到已有实体；
    本地已存在孪生行时改指向引用后物理删除本行（该行从未上云，物理删除安全）；
    ③ 客户端确定性去重通道（治已病）——每轮同步前 `mergeDuplicateRows`：
    同名组内保留 syncId 最小者（所有设备对同一组必然选中同一行），交易/周期账单/
    预算引用改指向，败者按「从未上云→物理删除 / 已上云→软删+DELETE 传播」退役；
    预算改指向撞 (year,month,category) 唯一键时保留既有行。已被污染的数据
    会在各设备下一轮同步自动收敛为每名一条，无需手工清理。
    服务端新增集成测试 `duplicateNamePush_mergesIntoExistingSyncId`（12 用例全绿）。
    附带修复：重构 `accepted()` 辅助方法时丢失 LWW 冲突标记的回归
    （`conflictingPush_lww_overrides_and_logs` 抓出）。
