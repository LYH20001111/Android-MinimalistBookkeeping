## 1. 目标与冻结口径

在一笔支出账单上登记「退款」，支持多次部分退款，并让退款正确地影响统计、余额、同步、备份与导入导出。

用户（2026-09-19）冻结了四条口径，全部取最大范围：

| 编号 | 决策点 | 冻结结论 |
|---|---|---|
| D1 | 净额是否参与统计与余额 | **参与**：统计与余额一律按「原额 − 已到账退款」计算 |
| D2 | 同步链路 | **全链路**：客户端协议升版 + 服务端 V5 迁移与新实体 |
| D3 | 可退款账单类型 | **仅支出**（收入 / 转账不提供退款入口，服务端与仓储层双重拒绝） |
| D4 | 退款状态 | **保留「待到账」+「已到账」**，并额外提供「已取消」终态供追溯 |
| D5 | 已登记退款可否回改 | **可以**（追加需求）：金额 / 原因 / 到账状态均可回改，含「退款中 → 已到账」直接切换 |

> D5 的落点：退款记录页每行未取消的流水加「编辑」入口，复用同一张退款表单（新增 / 编辑双模式）。
> 服务端无需改动——REFUND 推送本来就是按 syncId 的 LWW UPSERT，改状态、改金额都只是再推一次。
> 真正需要额外处理的是**额度复核要排除该笔自身当前的贡献**，以及编辑页返回后的额度快照刷新（见 §5 P1）。

由此推出的两条不变量（后续所有实现都服从它）：

- **待到账只占额度、不冲减钱**；只有已到账才改变统计与余额。
- **一笔账单的累计退款（已到账 + 待到账）不得超过原额。**

## 3. 数据模型与统计口径

### 3.1 新增表 `refund_record`

`data/entity/RefundRecordEntity.java`，15 列；外键 `transaction_id → transactions.id`，删除规则 **RESTRICT**（退款流水不得指向不存在的账单）；三个索引：transaction / sync_id / ledger_id。

状态机：`PENDING →（标记到账）RECEIVED`；`PENDING | RECEIVED →（撤销）CANCELLED`（终态，保留行不计入任何累计）。

### 3.2 账单两个累计列是「缓存」，不是真值

`transactions.refunded_amount` / `pending_refund_amount` 仅是缓存，真值永远在 `refund_record`。这与 `account.balance` 完全同构，因此沿用同一套治理手法：

- 任何写退款的路径都调用 `BookkeepingRepository.applyRefundTotals()` **从流水整体重算覆写**，绝不做增量加减；
- 每轮云同步结束后调用 `TransactionDao.recomputeRefundTotals()`（`TransactionDao.java:151-158`）对齐缓存；
- 每次备份恢复后同样重算；
- `recomputeRefundTotals()` 的 WHERE 只覆盖「有退款痕迹」或「缓存非零」的行，避免全表写。

### 3.3 净额的四条路径（原基线只写了三条，实现时补齐为四条）

任何一处漏改都会造成「列表金额与统计对不上」，故逐条落实并各有断言：

| # | 位置 | 口径 |
|---|---|---|
| 1 | `TransactionDao.NET_SUM` 常量 | SQL 聚合第一投影：type=1 用 `SUM(amount - refunded_amount)` |
| 2 | `TransactionDao.java:261` 第二处聚合投影 | 与 #1 同式（分类 / 日 / 月分组走这条） |
| 3 | `TransactionItem.netAmount()` → `StatisticsCalculator` | Java 侧计算，`isExpense() ? max(0, amount - refunded) : amount` |
| 4 | `AccountDao.BALANCE_EXPR` | 账户余额表达式，type=1 减去 `refunded_amount` |

**已记录的一处口径分歧（有意保留）**：SQL 侧不做非负钳位，Java 侧钳位。理由写在 `TransactionDao.java:35`——既然不变量保证 `0 ≤ 已退 ≤ 原额`，SQL 再加 `MAX(0, …)` 只会掩盖数据损坏；而 Java 侧面对用户输入与并发回读，需要防御性钳位。该分歧由 `netAmount_clampsAtZero` 单测固定。

## 4. 同步协议升版与服务端

- **协议版本 2 → 3**（客户端 `SyncProtocol` / 服务端 `ApiVersionFilter` 严格相等校验）。
- `REFUND` 是**第 7 个实体类型**。推送顺序 `SyncPayloadMapper.orderOf()`：LEDGER `-1`、CATEGORY `0`、ACCOUNT `1`、TRANSACTION `2`、**REFUND `3`**、BUDGET `4`、RECURRING `5`、未知 `6`。REFUND 紧跟其父账单之后，保证同批次内父账单先落库。
- 父账单尚未落地时服务端返回 **`MISSING_REFERENCE`**，客户端保留该变更并按退避重试，不丢数据。
- 服务端：JPA 实体 + Repository + `SyncService.applyRefund()` + 拉取投影，Flyway **V5** 迁移，`ddl-auto: validate` 要求列定义与实体严格一致。
- 服务端备份 `FORMAT_VERSION` 3 → 4；本地 JSON 备份 `SCHEMA_VERSION` 5 → **6**（`MIN_SUPPORTED_VERSION` 仍为 3，旧备份按「无退款」语义兼容）。
- CSV 追加 `已退款(元)` / `待退款(元)` 两列于**表尾**。`CsvParser.readColumns` 按名称前缀匹配、首个命中、忽略未知列，因此**只追加表尾对旧文件导入安全**。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 多设备并发退款导致累计超原额 | UI 只挡明显误操作，最终以 `requestRefund` 同一事务内的复核为准；缓存列每轮重算，不会漂移 |
| 缓存列与流水不一致（异常 / 崩溃路径） | 一律「重算覆写」而非增量加减；同步轮结束与恢复后各重算一次 |
| 列表原额与统计净额被用户视为 bug | 编辑页固定展示四行金额明细，文案直接解释差额 |
| 旧备份 / 旧 CSV 导入 | 版本下限不变，缺失退款字段按 0 处理；CSV 只追加表尾 |
| 退款指向已删除账单 | 外键 RESTRICT + 删除账单时级联软删退款流水、恢复时置回 |

### 6.1 升版连带破损（本轮实测发现并修复）

协议 / 数据库升版会**静默打断既有测试**，这类破损必须在合并前清掉：

1. `SyncProtocolRulesTest.pushOrder_referencesBeforeReferenced` —— REFUND 插入后 BUDGET / RECURRING / UNKNOWN 实际为 4/5/6，旧断言 3/4/5 **必然失败**。已改写并补齐 7 类。
2. `MigrationTest.openLatest()` —— 未注册 `MIGRATION_8_9`，导致该类**每个用例**都会抛 `A migration from 8 to 9 was not provided`。已注册并补退款断言。
3. `ServerHealthIntegrationTest` —— 协议 2→3 后旧字面量失效。已在上一轮修正为 4.0.0 / 3 / 4。

### 6.2 编辑页保存清零退款缓存（真机反馈，已修复）

现象链条：标记退款 → 金额明细正常显示 → **点保存**后，记录页的「已退 / 退款中」角标与编辑页金额明细同时消失，再次标记退款提示「退款未生效，请刷新后重试」。

根因不在退款写入，而在账单更新写序：`TransactionEditActivity.save()` 构造的是只含表单字段的「半实体」，`saveTransaction` 更新分支走 Room 整行 `@Update`，而 `carryTransactionMetadata()` 当时只回填了 syncId / version / isDeleted / ledgerId，**漏了 `refundedAmount` 与 `pendingRefundAmount`**，于是这两列被写成 0。角标与明细都读这两列故消失；而额度复核 `RefundPolicy.isRequestValid` 读的是真值 `refund_record` 累计，与刚被清零的缓存冲突故拒绝。

两处修复：

1. `BookkeepingRepository.java:151-155` —— 保存时带过两列。真值虽在 `refund_record`、每轮同步会 `recomputeRefundTotals()` 兜底重算（因此该 bug 表现为「刷新后有时又好了」），但保存当刻必须正确，不能让展示依赖一次同步。
2. `TransactionEditActivity.java:301-307` —— 新增 `onResume` 回读快照。`source` 是按需快照而非订阅，从退款记录页改完退款返回时不回读就一直显示旧额度。`onSourceLoaded` 里 `renderAmountDetail` 排在 `formApplied` 短路之前，故刷新明细不会覆盖用户正在编辑的表单。

同期新增「编辑已有退款」能力（金额 / 原因 / **到账状态可回改**），入口在退款记录页每行的「编辑」，落在 `BookkeepingRepository.updateRefund`：额度复核从 `refund_record` 累加**排除该笔自身**，已到账改回待到账时清空 `receivedAt` 并把余额冲减撤销。服务端 `applyRefund` 是普通 LWW UPSERT 且 `state` 为必填、`receivedAt` 可空，**改状态无需服务端改动**。

> 生效时机：见 §6.3——最终按产品要求改为**暂存**，编辑页只有点保存才落库。

### 6.3 编辑页退款改为暂存（真机二次反馈后的定稿）

修复 §6.2 后用户在真机上仍复现「保存后角标消失」，且明确表达诉求：**「只有通过点击保存按钮后，退款相关内容才能被保存，点击返回不能保存」**。

排查记录：仓库层与 DAO 层都没有第二处覆写点（全仓 `refunded_amount =` 的 UPDATE 只有 `recomputeRefundTotals()` 一条，`getEntityById` 是 `SELECT *` 故 carry 能读到真值），而 `app/apks/` 与 `app/build/outputs/apk/debug/` 里最新的构建产物是 9 月 6 日的 3.2.0 —— **当时设备上跑的包不含 §6.2 的修复**。暂存改造无论如何都更稳，因此按用户要求实施，而不是继续等一次带修复的构建。

实现口径（4 个文件）：

1. `TransactionEditViewModel` 新增 `DraftRefund` 与 `draftRefunds` LiveData（放 ViewModel，旋转屏幕不丢草稿），配 `addDraftRefund` / `clearDraftRefunds` / `draftReceivedTotal` / `draftPendingTotal`。
2. `TransactionEditActivity.showRefundSheet()` 改为**只追加草稿**，额度基数取表单当前金额（保存后真正生效的就是那个额），可退额度并入草稿累计。
3. `renderAmountDetail()` 把草稿并入「已退款 / 待退款」两行，口径与保存后完全一致。**不单独显示「待保存退款」提示行，也不给撤销按钮**（用户看过截图后明确要求去掉——明细已反映金额，多一行提示与一个按钮只是噪音）。唯一的「本次会同时落退款」披露留在保存前确认弹窗里（`edit_amount_draft`）。
4. `performSave()` → `commitDrafts()` **串行**提交（每笔都要看到前一笔已写入的累计才能复核额度，并行会让超退草稿蒙混过关），被拒的不重试、末尾统一提示；`save()` 的金额下调守卫与保存按钮小圆点都计入草稿。

边界：草稿不落库故无同步与编辑日志，也就没有「退款了但账单没保存」的中间态；退款记录页（管理页，无保存按钮）仍保持即时生效。

### 6.4 金额明细卡片化与菜单图标（真机截图后的样式微调）

1. **金额明细**改成 `MaterialCardView`（`Widget.App.Card`）+ 四行「左标题 / 右数值」，`实际支付` 前用现成的 `@style/AppDivider` 收尾并升到 `TextAppearance.App.Body` 加粗；配色 原始金额 `text_secondary` / 已退款 `success` / 待退款 `warning`。`renderAmountDetail()` 因此只写数值，行显隐改到新加的 `amountDetailRefundedRow` / `amountDetailPendingRow`（标题成了静态控件，不能再靠隐藏整行文本），并删掉 `detailLine()` 拼接。
2. **右上角菜单三项配图标**（价签¥ / 单据+时钟 / 铅笔）。两个坑记录在此：①溢出菜单默认**不显示图标**，必须打开 `MenuBuilder.setOptionalIconsVisible(true)`。**这里踩过一次编译错误**：先前写成 `androidx.core.view.MenuCompat.setOptionalIconsVisible(...)`，并以为「appcompat 1.8 起是公开 API」—— 实际拆了本地 gradle 缓存里 core 1.13.1 / 1.16.0 / 1.19.0 三个 `MenuCompat.class`，常量池里只有 `setGroupDividerEnabled` 和 `setShowAsAction`，**这个方法根本不存在**；且 appcompat 1.8.0 的 pom 里 compile 依赖就是 core 1.13.0，升级依赖也拿不到。最终落为 `TransactionEditActivity.showIconsInOverflowMenu()`：`instanceof MenuBuilder` 后直接调用，类上标了 `@RestrictTo` 所以 javac 放行、lint 会报 RestrictedApi，方法加 `@SuppressLint("RestrictedApi")` 局部压掉（`Toolbar` 内部持有的正是 `MenuBuilder`，转换必然成立）。②仓库里通用 `ic_*` 全是 `fillColor="@android:color/white"`，靠使用处 tint 上色，而菜单弹窗不给图标着色 —— 直接引用会在白底上**完全看不见**，故新建 `ic_menu_refund` / `ic_menu_refund_history` / `ic_menu_edit_history` 三个自带 `android:tint="@color/text_primary"` 的矢量图（minSdk 24，不能用 API 26 才有的 `android:iconTint`）。

真机手工回归清单：①单笔全额退款 → 统计与余额同步下降；②两次部分退款 + 一次待到账 → 只有已到账部分冲减；③取消已到账退款 → 金额还原；④删除账单 → 回收站恢复后退款累计与展示均正确；⑤双设备并发退款 → 后到的一方被拒绝且不产生脏数据；⑥旧版本备份恢复到 4.0.0 → 无退款数据且统计不报错；⑦**标记退款后点编辑页保存 → 记录页角标与金额明细都必须保留，且能继续退第二笔**（§6.2 的原始复现路径）；⑧退款记录页把「待到账」改成「已到账」再改回 → 余额随之冲减 / 撤销，返回编辑页额度立即刷新（不必退出重进）；⑨**标记退款后直接点返回 → 记录页不得出现任何退款角标，编辑页再进来也不得有（草稿已丢弃）**，且重复「退款 → 保存」「退款 → 返回」两轮都不产生多余退款流水；⑩编辑页连加两笔草稿（一笔已到账、一笔待到账）→ 明细行合并显示且额度递减正确，保存后库里恰为两笔，余额只按已到账那笔冲减。
